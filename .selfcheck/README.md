# .selfcheck —— PC 端编译自检与回归探针

这个目录**不参与烧录**，只是让你在电脑上（不需要 Arduino 板子）验证固件的
语法、类型、运动学模型与手柄逻辑。烧录时忽略整个目录即可。

> 当前固件是**角度模式**：摇杆直接改变 4 个舵机角 `Pos.ser.angle1..angle4`，
> 且串口 `x/y/z` 也直接写这三个舵机角（不做逆解）；
> `Pos.rec.x/y/z` 是由正运动学 `recFromServo()` 算出的派生显示量。
> 旧的"末端坐标控制"版本备份在仓库内：分支 `backup/xyz-cartesian`（= tag `v1.6.3`）
> 与 `dist\meArm_xyz_cartesian_v1.6.3_source.zip`。

## 为什么需要它

`arduino-cli` 没有装，无法做真正的 AVR 编译；而历史上真正致命的错误
（`#endif}` 少一个花括号、`-Wenum-compare` 枚举混用、`-Wunused-but-set-variable`）
**全部是编译器抓到的，人工审查两次都没看出来**。所以改动固件后请务必跑一遍这里。

更要紧的是：这套自检抓到过**探针自己写错、反过来冤枉固件**的多次假失败
（详见下面"写新探针时的教训"），也抓到过真正的固件 bug。

## 工具链

- 编译器：`C:\ProgramData\mingw64\mingw64\bin\g++.exe`（16.1.0）
- mock 头文件在本目录 `mock\`：`Arduino.h`、`Servo.h`，仅用于 PC 端替代真机 API。
- 串口日志默认被丢弃；想看到固件里的 `Serial.println` 输出，先设环境变量
  `$env:WEARM_MOCK_SERIAL='1'`。

## 一键跑全部

```powershell
D:\dsh1\meArm\.selfcheck\run_all.cmd
```

（`.cmd` 只是个壳，用 `-ExecutionPolicy Bypass` 调 `run_all.ps1`——
Windows 默认禁止直接运行 `.ps1`。）

它做两件事，任一失败就 `exit 1`：

1. **严格编译 9 个固件 TU**（`-Wall -Wextra -Wshadow -Wconversion`），要求
   **零警告**；
2. **编译并运行 11 个自检程序**，逐个要求输出里有 `ALL PASS` 且退出码 0。

每个探针的完整输出会存到 `.selfcheck\out\<探针>.log`。

### 当前实测包络（r、c 都放开到 0~180 之后）

```
x[-40.00, 40.00]  y[-40.00, 40.00]  z[-20.00, 40.00]
limit    : x[-40.0,40.0] y[-40.0,40.0] z[-60.0,60.0]
余量     : x[0.00,0.00] y[0.00,0.00] z[40.00,20.00]   （非负 = limit 完整覆盖包络）
```

四个极端姿态：`x=+40` 在 (b,r,c)=(90,0,0)，`x=-40` 在 (90,180,0)，
`z=+40` 在 (90,90,0)，`z=-20` 在 (90,0,90)。

逐高度（每 2° 一层，y 恒为 `[-X, X]` 对称）：`z=0.0 → x[-40.00,40.00]`（最远）、
`z=-20.0 → x[0,26.18]`、`z=20.0 → x[-35.15,35.15]`、`z=40.0 → x[-8.66,8.66]`。

两点容易看错，先说明：

- 每一层是 `|z - 层高| <= 1` 的**一层**，不是"z 恰好等于层高"的精确平面。
  所以 `z=40.0` 那层不是 0 而是 ±8.66 —— 它含了 `z=39.05` 的姿态
  （`r=103,c=1` 给 -8.66；`r=78,c=1` 给 +8.66）。真正的 z=40 只有
  `(r,c)=(90,0)` 一个姿态，此时 x=y=0。
- 负 x 来自 **ρ<0 的"朝后伸直/反折"姿态**（`20cos(r)+20cos(r-c)` 变负），
  例如 `r=180,c=0` 时 ρ=-40，b=90° 就落在 x=-40。不是算错。

## 写新探针时的教训（都踩过，代价很大）

1. **直接 `#include "constant_and_positions.h"` 调用固件函数，不要重写公式。**
   探针里重写运动学必然引入符号错：曾经把基座角写成 `theta=(b-90)`（应为
   `(90-b)`），整张可达表镜像，于是把"可达"误判成"不可达"，浪费好几轮。
   `wearm_ino_test` 同理：**直接 include 真 `.ino`**。手抄复刻版曾把引脚写成
   9/10/11/6（真 sketch 是 9/7/8/6）却照样编译通过、零警告——
   接线漂移只有"直接编译真文件 + 核对行为"才抓得到。
2. **必须调 `servoSelfCheck()` 再反解**，否则 `jointMin/jointMax` 映射表仍是全 0，
   会把所有角度夹成 0（表现为打印全 0.00、可达率虚高）。
3. **不要把 `getAngle(&t)` 和读取 `t.ser.*` 写在同一个 `printf` 参数里** ——
   参数求值顺序未指定，会打印出"陈旧但看起来合理"的角度。先 `bool ok = getAngle(&t);`
   再打印。
4. **循环边界别硬编码关节行程**（`c <= 105` 这类）。行程一改（c 已从 105 放到 180），
   探针就悄悄只测一半网格。改成从 `0.0/maxC` 取。
5. **探针自己报的失败要先怀疑探针。** 踩过的假失败：
   - "慢速测试的终点接着测快速，剩余行程不足导致快速位移反而更小" ——
     两次测量前都要 `resetInputs(); posInit();` 回到同一起点；
   - 把**不在 `limit` 体积内**的点（如 x<0）当反解失败 —— 那些点会先被盒子判据
     挡住（v1.6.4 是 `clampToRange()`，该函数在 v1.6.5 删除、本轮只恢复了盒子本身），
     应先用 `limit.minX/maxX/...` 过滤；
   - 用 `==` 比较浮点角度：`posInit()` 走"设坐标→反解→落角度"往返，
     角度带 ~1e-13 舍入误差，`89.99999999999999 != 90.0` 会报假失败
     （而 `%.1f` 打印出来完全正常）→ 用容差比较。

6. **串口必须单一读者**。旧函数 `handleSerialSpeedCmd()` 自己调用 `Serial.read()`，新的行缓冲也要读同一串数据，两个读者会把字节各吃一半、行永远拼不完整。因此旧函数已**整体删除**（连同 `constant_and_positions.h` 里的声明），串口字节只由 `serialProtocolLoop()` 读，调用点只在 `meArm.ino` 的 `loop()` 里（放在 `joystickLoop()` 之前）。`joystickSetup()` 也不再调用 `Serial.begin()`。
7. **mock 的串口输入缓冲只有 64 字节且只追加不压缩**：`.selfcheck\mock\Arduino.cpp` 里是 `static char inBuf[64]`，`mockSerialFeed()` 只 append，读空后 `inPos` 等于 `inLen` 但 `inLen` 不回退。所以连续喂超过 64 字节的测试，后面的字符根本进不去 —— 测的是 mock 缓冲被塞满，而不是固件行为。正确做法是穿插 `mockSerialClear()`（或分段重建缓冲）。反例：`probe_protocol` 原超长行用例注释写"60 个 A"，字面量实际是 70 个，行尾换行符根本没能进缓冲。
8. **无换行超时用例必须调用两次 `serialProtocolLoop()`**：固件在读到字符时把 `s_lastCharMs` 记成 `millis()`，若先喂数据、再一次性推进 400 毫秒、再调 loop，则超时判断里的时间差恒为 0。正确写法是先 `mockSerialFeed` 再调一次 loop，再 `g_mockMillis` 加 400，再调第二次 loop。
9. **mock 的 `MockSerial` 没有 `print` 的单字符重载**：写 `Serial.print(某个 char 变量)` 会被隐式提升到打印 int，串口里打出的是码值（例如字母 x 打成 120）。要打印单个字符必须用长度 2 的 C 串（`char ch[2] = { c, 0 }; Serial.print(ch);`），真机与 mock 都能出字母。
10. **`PROTO_ANGLE_MIN` 与 `PROTO_ANGLE_MAX` 已被删除**：本工程不为解析阶段定义名义角度区间。解析时不该因为角度超出某个区间就拒绝指令（那样 x200 就变成废指令），而是落地前按该关节真实的舵机电气行程（b/r/c/f 都是 0~180）夹取（x200 最终写 180）。探针要造随机角度请用自己的局部常量。
11. **探针直接赋值 `Pos.ser` 会造出固件永远不会产生的脏状态**：探针的 `resetInputs()` 直接写 `Pos.ser.angle1` 到 `angle4`，不走固件写入路径，因此 `Pos.rec` 不刷新；而固件唯一写角度的地方 `protoApplyAngles()` 在 `written` 大于 0 时会调一次 `recFromServo(&Pos.rec, &Pos.ser)`，即固件任何一次成功写入都保证 `Pos.rec` 自洽。曾因此在压力测试里出现 violations 等于 4 的假警报（全是"Pos.rec 必须等于 recFromServo(Pos.ser)"这一条不变量）。正确做法：压力测试开始前自己补一句 `(void) recFromServo(&Pos.rec, &Pos.ser);`。
12. **PowerShell 的逗号优先级高于加号**：把两个 `-I` 参数用 `@("-I" + $root, "-I" + $mock)` 这样写会拼成**一个**字符串，表现为编译报 `fatal error: Arduino.h: No such file or directory`。必须给每个拼接加括号。
13. **给子智能体的长文本（例如 workflow 脚本里的 prompt）不能出现反引号**：脚本里用模板字符串包住 prompt 时，正文里的 markdown 反引号会直接终结模板字符串，报 `workflow script does not parse` 与 `SyntaxError: Unexpected identifier`。
14. **探针不许引用只存在于某个 `.cpp` 里的私有宏**。`pick_place.cpp` 的 `PICK_GRASP_Z` / `PICK_APPROACH_DZ` 是文件内 `#define`，探针 include 了头文件也看不到它们（表现为 `'PICK_APPROACH_DZ' was not declared`）。修法不是把宏抄一遍（那会制造第二处真值），而是在头文件里加一个访问器：`double pickPlaceApproachDz(void);`。
15. **`REC` / `SER` / `pos` 是 `typedef`，不能写 `struct REC r;`**（C 语言习惯，C++ 里报 `expected primary-expression`）。写 `REC r;` 即可。
16. **子智能体说"编译通过/测试通过"一律要自己再验一遍**。本轮一个子智能体在**从未编译成功**的情况下写出"预期输出应该是所有测试通过"，还往 `.selfcheck\` 扔了 11 个一次性垃圾文件（`hello.c`、`probe_minimal.py`、`probe_report.txt` 之类）。验收口径：自己跑 `run_all.cmd`，看它在**你改完的磁盘文件**上是否真的全绿；子智能体贴的原始输出只当线索，不当证据。
17. **测"某期间摇杆被让位"时，别把"期间结束的那一瞬间"算进去**。`probe_button` 的收尾循环写的是 `buttonLoop()` 之后紧接着 `joystickLoop()`：播放恰好在 `buttonLoop()` 里收尾，于是同轮的 `joystickLoop()` 立刻用还按着的摇杆走了 1.0°（`angle2 86.1124 -> 85.1124`），报成"让位失效"。固件是对的 —— 播放一结束摇杆就该立刻恢复。正确写法：循环条件用 `buttonControlLocked()`，并且**只在仍然锁着时才调 `joystickLoop()`**，然后单独收尾跑完剩余流程。
18. **探针里对"循环序号"这类有状态的量，不要写死第几次的期望值**。`probe_button` 断言"mock 喂 `N\n` 应该夹 A"，但循环序号在前面用例里已经推进到 C，于是假失败。正确写法：调用**前**先取 `int nextBefore = buttonPickNext();`，再断言 `pickPlaceCurrentObject() == nextBefore`。
19. **用 `edit` 工具改 `.ps1` 会丢 UTF-8 BOM**（第 274 行那条坑的另一面：`write`/`edit` 都按无 BOM 写）。改完必须补：读成字节、前置 `EF BB BF`、`[System.IO.File]::WriteAllBytes()` 写回，再确认 `CRLF` 数正常、`loneLF` 为 0。`run_all.ps1` 因为要被 `powershell -File` 解析，BOM 丢了会直接语法报错。
20. **`run_all.ps1` 的汇总行用 `$probes.Count` 自动计数**，加探针不用手改文案；但 `README.md` 里的"6 个固件 TU / 7 个自检"是手写的，每加一个 TU 或探针都要同步改示例输出，否则文档与实测输出对不上。
21. **"缓冲能撑多久"必须按最坏情况的每周期条目数推一遍**。`button_control.cpp` 头部原写"条目速率上限约 25 条/秒、512 条 ≈ 20 秒"，把采样周期误当成了条目速率；实际每个有动作的周期最多写 `1 + 动的关节数` 条 → 四关节同时动 = 125 条/秒，512 条只够 4.1 秒 → 必然写满、必然低于 10 秒门槛、录完就判废。修法是换格式：把"推进一个周期"塞进增量条目的 bit7（`BTN_TICK_FLAG`），每周期只花"动了几个关节"条，并把 tick 从 40 ms 放宽到 100 ms；容量结论按 `512 / (1 + 关节数) × tick` 重算后才写进注释。**后续补充**：这一版格式与"最小时长"门槛后来都被又一轮重构换掉了 —— 现在是每个 200 ms 周期（`WEARM_REC_TICK_MS`）固定写一条 **4 字节**记录（四个关节各 8 位有符号增量），`WEARM_REC_ENTRIES` = **192 条 = 38.4 s = 768 B SRAM**，而"时长必须 >10 s"这条门槛**已被删除**（只剩位移门槛）。教训本身（容量必须按最坏情况推算、结论写进注释前先复测）仍然成立，而且**字段位宽也必须按最坏情况推算** —— 见教训 22。
22. **"周期性采样 → 回放"必须显式处理首尾零头**。采样是离散的，`btnRecTick()` 只在周期边界结算增量，于是"最后一个整周期 → 松手"之间的动作永远进不了缓冲。四关节在快速档每周期能走 10 度，回放终点就整整差 10.00 度（不是量化误差，是丢了一段）。修法：`btnStopRecording()` 一开头调 `btnRecFlushTail(now)` 把这一小段补成条目，只有跨进新周期时才给第一条挂 `BTN_TICK_FLAG`。修完 `probe_button` 的末态差从 `10.00/10.00/10.00/9.50` 变成 `0.00/0.00/0.00/0.00`。**后续补充（采样周期放宽到 200 ms 之后）**：这条教训又咬了一次，而且这次是**两个原因叠在一起**——(a) 记录字段只有 6 位（±16 度/条），200 ms 一周期时正常档就能走 20 度，超出的部分全靠 `s_snap[]` 顺延，于是每个周期都在积压；(b) 收尾只补**一条**记录，积压的尾巴被截掉，于是四轴同时全速时回放终点短 10~13.5 度。修法是同时把字段放宽到 **8 位（±63.5 度/条 = ±317 度/秒 @200 ms）**、并把收尾改成**排空循环**（最多 8 次，直到没有新增量）。**结论：字段位宽也是"最坏情况"的一部分，"补一条"永远不等于"排空"。**
23. **"每轮最多走多少度"的限速，不能拿循环周期当时间基准去卡事件驱动的动作**。`draw_control.cpp` 的 `tryApplyPoint()` 原来用 `DRAW_MAX_DPS * s_dtSec`（`s_dtSec` 是 `drawLoop()` 的循环周期，PC 探针里 5 ms → 上限 0.55°）做每轮上限。这对"每轮都写一个轨迹点"的路径跟随是对的，但**示教点动是事件驱动的**（每 10~40 ms 才动一次，一步 1.4~2.9°；当时的间隔字段叫 `fullDelayMs`/`minDelayMs`，v1.6.4 起已换成单一的固定值 `speed.stepDelayMs`），于是每一次点动都超限被整条拒绝 —— 上机表现就是"摇杆推了笔尖不动"，而路径跟随一切正常。修法有两条：(a) 让时间基准变成**距上次真正写入点位的时长** `applyDtSec()`（夹在 `[0.005, 0.1]` 秒，顺手防住长时间暂停后的巨大跳变），(b) 点动这种手动模式用**夹取**而不是拒绝（新增 `applyPointClamped()` 与 `DRAW_JOG_MAX_DPS 200`），因为手动点动只要求"大致往那边走"，被拒一次就等于卡死。
24. **"开始/结束一段动作"的辅助函数只装参数、不改阶段，别指望它顺手把状态也改了**。`drawCancel()` 的"绘制中取消"分支写了 `beginLift(lz); s_nextAfterMove = RETURN;` 却漏了 `s_phase = DRAW_PHASE_LIFT;`，于是取消后阶段还停在 TRAVEL/PLUNGE/PATH，状态机接着按原轨迹继续画 —— **取消等于没取消**（探针里表现为"取消后立刻进入抬笔阶段 FAIL"）。同文件"画完自动抬笔"那处三行齐全，就是靠对照才发现漏了一行。写这类状态机时，"设置下一阶段"和"装移动参数"必须是两个显式动作。
25. **"阶段没进顺序表"与"阶段顺序错"要分得清**。`probe_draw` 的 `runToIdleTrace()` 原来在 `drawGetPhase() == IDLE` 时**直接 return、不采样**，于是"回到空闲"这一步永远不出现在阶段顺序里，检查 `seqBefore(结束回待机, 空闲)` 假失败。同理，若在示教前不清空顺序表，`seqBefore(准备绘制, 回待机)` 会撞上"示教前那次回待机"，也假失败。修法：返回前补记一次采样；并且在"只关心某一段"的检查前 `seqReset()/traceReset()`。
26. **C++ 函数实参的求值顺序是未指定的**，别把"先调它、再读它"写成 Check 的两个实参。`check("选中五点折线", drawSelectTask(DRAW_TASK_POLYLINE) == DRAW_TASK_POLYLINE, drawTaskName(drawGetTask()))` 里的 `drawTaskName(...)` 可能先于 `drawSelectTask(...)` 求值，于是详情里印的还是**上一个**任务名（看起来像"选错了任务"）。修法：先 `(void) drawSelectTask(...)`，下一行再读状态。

1. **`C:\msys64\ucrt64\bin\g++.exe` 在本沙箱下静默失败**：退出码 1、stderr 一个字都没有、连 `-v` 都不打印，`.exe`/`.o` 永不产出（看起来像"什么都没发生"）。**一切编译/链接都用 `C:\ProgramData\mingw64\mingw64\bin\g++.exe`** —— 它也是 `run_all.ps1` 里 `$gpp` 用的那一个。

## 固件里的坑（自检抓到过的真 bug）

写固件时这几条都是"看起来对、实际错"的，已修：

1. **`clampToRange()` 会原地改 `Pos.rec` 并返回"是否夹到过"**，不能当只读判断用。
   旧 `moveJointStep()` 为了"给坐标一个临时落点"先挪坐标再判断越界，
   结果越界时该函数把坐标夹回边界值、返回值恰好让整步回退被跳过，
   末端坐标能停在界外（压力测试报 `violations=5722`）。修法是新增只读的
   `posOutOfRange()`，整步回退。
2. **`isReachable()` 判断 `R > L1+L2` 必须带浮点容差**。两杆完全伸直时 R 数学上
   恰为 40，浮点算出来是 40.000000000000004，严格比较会把"全伸直"整类姿态
   判成不可达（实测 19 组反解失败）。现在用 `GEOM_EPS = 1e-9`。
3. **`90 - RADtoDEG*atan2()` 的浮点误差会把"正好 0°"算成 -2.4e-10**，
   归一化 `while (b < 0) b += 360` 于是把它变成 359.9999999998，
   再和 `maxB = 180` 一比就丢掉这个分支：目标 `(0,20,20)` 的正确回转角恰好是 0°
   就踩在这里（表现为反解 false、`Pos.ser` 停在 `(0,0,0)`）。
   修法：归一化后把 `> 360-1e-6` 的值折回 0°。
4. **反解要试 4 个候选**：`{rhoP = ±rho} × {delta = ±|c|}`。
   只试一个分支会漏解（镜像姿态里常常只有一个满足机械行程）；
   而 `rhoP = -rho` 的反向平面分支是 `x<0` 类目标的唯一出路
   （正向平面会算出 190°~270° 的回转角，超出 `b` 的行程 `[0,180]`）。
5. **舵机角 `c = alpha - beta`，不是 `beta`、也不是 `|c|`**。模型是
   `beta = alpha - c`，所以反解必须先求出 `alpha` 与 `beta` 才能得到 `c`。
   曾把 `beta` 或 `|c|` 直接当舵机角，导致 `(28.28,0,0)` 这类点"解"残差很大。
6. **单个标定点无法区分模型**：`beta = r-c`、`r+c-180`、`180-r-c` 在 c=90 时
   全部退化成同一个点 (20,20)，只有代 c=105 才分道（正确模型给 (19.32,14.82)，
   `r+c-180` 给 (19.32,25.18)）。**凡是"唯一命中"的结论，先找第二个参数不同的标定点。**
7. **`getAngleEx()` 返回 false 时不能改 `Pos.ser`**。`applyJointLimits()` 在 CLAMP
   策略下就地吸附，写完才发现要拒绝时角度已被改掉一半——
   老代码踩过：一个反解失败的 `posInit()` 把 `Pos.ser` 留成 `(0,0,0)`，
   **上电时机械臂直接甩向原点**。现在先存 `oldA1..oldA4`，失败全部回滚。
8. **夹限位判断的容差不能用 `ANGLE_EPS = 1e-6`**：反解落在行程端点上的解常有
   -1e-14 量级舍入误差，于是几乎每个"正好在端点"的姿态都被判越界，
   `clamped` 标志天天误报。改用 `LIM_EPS = 1e-9`（远小于舵机可分辨的 0.1° 步进）。
9. **固件只能有一处运动学实现**。`posInit()` 的开机自检曾自己重写正解并写成
   `(angle2 + angle3)`（应为 `r - c`），公式错了照样打印一串"看起来很合理"的数字。
   现在整段改成调用固件自己的 `recFromServo()`。

10. **反解的"镜像分支"不是 bug，但必须用正解回代验证。** 同一个末端点可以有两组
    关节角到达：基座转 180°、两节臂在相反的竖直平面里镜像，两组都合法，反解器
    只能给出其中一个。r 放开到 0~180 之后镜像解也落进了行程，反解器可能先选到
    它，于是只比回转角就会误报 180° 的"误差"（实测 22 组）。修法**不是**放宽阈值
    或跳过这些点，而是**加强**判定：镜像分支（回转角与原来相差 180° 左右）必须用
    固件 fk() 正解回代、残差 < 0.05 才算通过，否则计入 branchBad 判 FAIL。
    （实测 1950 组里 22 组是合法镜像解，无法解释的 0 组。）

    （爪子的全开/全关由 `O`/`S` 覆盖，步进由摇杆 A2 覆盖）。结果码 `5` 因此留空，

- **串口协议处理**（`serial_protocol.h` 与 `.cpp`）：
  - 字符读取、行缓冲、命令解析与落地写入
  - `!` 查询当前功能状态（P=取放、B=按键、D=绘图）；`!P` / `!B` / `!D` 切换运行时启用状态。只能切换编译进固件的模块，无法开启编译裁掉的代码。
  - 开启 `WEARM_SERIAL_RESPONSES` 后，每条识别命令都回一行短回复：
    `OK`（O/S 带夹爪角度 `OK #`、`x/y/z` 角度指令、`F` 换任务带模式 `OK F=<tag>`）、`BUSY`（懂了但现在忙）、`OFF`（模块被 `!P/!B/!D` 关掉）、
    `DISCARD`（R 结束录制时数据不合格已丢弃）、`EMPTY`（P 没有录制数据）、
    `ERR`（语法错）、`REJECTED`（固件没编进该模块 / 轨迹校验不过）。
    先确认串口助手设为 115200 baud，并且固件已烧录。
  - 对外接口：`serialProtocolBegin()`、`serialProtocolLoop()`、`protoHandleLine(const char*)`
  - 命令语义：`O`=爪子开、`S`=爪子关、`H/L`=速度档升降、
    `x20,y0,z40`=把 x/y/z 编号的三个舵机分别写 20/0/40 度（超出舵机电气行程 0~180 按行程夹取，见下面"角度语义回归"一节）

- **探针更新**：
  - `probe_joystick` 中的旧串口用例已删除，移至 `probe_protocol` 专门测试
  - `probe_protocol` 探针现有 12 段，专门测试串口协议功能（含 3000 轮随机角度压力）

## 新增 A/B/C 自动取放模块

本轮新增 `pick_place.h` / `pick_place.cpp`：上位机发送单个字母 `A` 或 `B` 或 `C`，
机械臂自动把对应物体夹起来搬到另一个位置。

- **对外接口**（`pick_place.h`）：
  - `int pickPlaceStart(int object)`：启动某个物体的取放序列。返回 `0` 已启动、
    `-1` 编号非法、`-2` 已有序列在执行、`-3` 路径校验失败（**失败时不改任何全局状态**）。
  - `void pickPlaceLoop(void)`：非阻塞推进，每轮 `loop()` 调一次，不调用 `delay()`，
    不做等待式循环。
  - `bool pickPlaceIsBusy(void)` / `int pickPlaceCurrentObject(void)` / `const char *pickPlaceStageName(void)`
  - `bool pickPlaceGetSource(int, double*, double*, double*)` / `...GetTarget(...)`：
    读出物体初始位置与放置位置。
  - `double pickPlaceApproachDz(void)`：接近点相对物体的抬升高度（探针用它，避免抄死 6.0）。
  - 物体编号：`PICK_OBJECT_A/B/C` = 0/1/2，`PICK_OBJECT_COUNT` = 3。

- **位置表**（都写在 `pick_place.cpp` 顶部，改这里即可自定义）：

  | 物体 | 初始位置 | 放置位置 | x 位移 | y 位移 |
  |---|---|---|---|---|
  | A | (24, 12, 12) | (16, -14, 12) | -8 | -26 |
  | B | (24, -12, 12) | (18, 16, 12) | -6 | +28 |
  | C | (12, 20, 12) | (28, -6, 12) | +16 | -26 |

  三个初始点两两相距 24.00 / 14.42 / 34.18，三个放置点两两相距 30.07 / 14.42 / 24.17。
  另外每个放置点离**别人**的初始点都 ≥7.21（实测最近的是三对并列：B 放对 A 初始、B 放对 C 初始、
  C 放对 B 初始，都是 7.2111），免得给一个物体放件时夹爪蹭到还在地上的另一个物体。

- **动作拆解**（每个物体都是这套）：到物体上方 → 垂直下降到抓取高度 → 合爪
  （`angle4` 写成 `60.0`，与串口 `S` 同角度）→ 停顿 400ms → 垂直抬起
  → 平移到放置点上方 → 垂直下降到放置高度 → 张爪（`150.0`，与 `O` 同角度）
  → 停顿 400ms → 垂直撤离。

- **启动前校验**：把 6 段直线按 0.5 的步长采样（每段最多 64 点），逐点要求
  "在 `limit` 内 + `isReachable()` + 反解成功且未被吸附"，且相邻采样点的关节角
  跳变不超过 25°（防止反解中途换分支）；还要求当前位姿与手里角度同分支（差 ≤10°）。
  任何一项不过就拒绝启动并保持现状 —— 宁可不动，也不能半路甩臂。

- **串口集成**：`serial_protocol.cpp` 在单字符命令 `switch` 里加了 `A/B/C` 三个分支，
  返回 `PROTO_RES_PICK_STARTED`（10）或 `PROTO_RES_BUSY`（11）；序列执行期间
  `protoHandleLine()` 最前面有忙守卫（`pickPlaceIsBusy() || buttonControlBusy()`），
  **只放行调速指令 `H/L` 与按键命令 `N/R/P/M`**，其余动作指令
  一律返回 `PROTO_RES_BUSY` 且不改状态，并回一行
  `[proto] busy: pick/place or record/play running, command ignored`（在
  `#if WEARM_DEBUG_SERIAL` 里，不影响返回值）。摇杆侧在
  `joystick_control.cpp` 的轴步进循环开头 `if (pickPlaceIsBusy() || buttonControlLocked()) break;` ——
  序列执行与播放/回中期间独占 b/r/c 与末端角（录制期间**不**独占，见下一节）。
  D13 指示灯把"序列在执行"也算作在动（`updateLed(moved || pickPlaceIsBusy() || buttonControlLocked())`），
  否则那十几秒灯是灭的，看着像死机。

## 新增四按键操作接口

本轮新增 `button_control.h` / `button_control.cpp`：四个按键的全部调用接口都封装在
**这一个 cpp** 里（这是需求原文的硬性要求），`meArm.ino` 只调 `buttonSetup()` /
`buttonLoop()`。

- **按键接线**：D2 = 按键1（循环执行取放）、D3 = 按键2（录制）、D4 = 按键3（播放）、
  D5 = 按键4（回中）。四脚 `INPUT_PULLUP`，按下为**低电平**（另一端接 GND），
  25 ms 时间消抖，只认按下沿。D6~D9 是舵机、D13 是灯、D0/D1 是串口、A0~A3 是摇杆，
  D2~D5 是唯一空闲好接的四个脚。
- **串口等价命令**（外部接口不只在按键上）：`N` = 按键1、`R` = 按键2、`P` = 按键3、
  `M`（别名 `0`）= 按键4。**不用 1/2/3/4**：数字键不与任何已占用的命令冲突，
  但用字母可以让一组命令在串口助手里一眼分辨出是按键等价命令。
- **按键1 循环执行**：每按一次依次夹 A、B、C，第四次回到 A。忙时（序列执行中）
  被拒绝且循环序号**不推进**。
- **按键2 录制**：第一次按下开始录（状态「录制中」，串口回 `PROTO_RES_REC_STARTED`=12），
  人工用摇杆操控；第二次按下结束并保存（13）。保存门槛**只剩一条**：末端在 x/y/z 的
  包围盒跨度（`btnTravelSpan()`）**≥10.0**（`BTN_REC_MIN_TRAVEL`）。**没有最小时长限制**
  ——原来还要求"录制时长 >10000 ms"（`BTN_REC_MIN_MS`），**已按要求删除**：1 秒的动作
  只要真走够了位移就照样保存。不达标回 `PROTO_RES_REC_REJECTED`=14。**录制失败会连带
  废掉上一次的录制**（缓冲区已被本次录制复用），代码注释与串口提示都写明了这一点。
- **录制格式**：每个 200 ms 采样周期（`WEARM_REC_TICK_MS`）写**恰好一条** 4 字节记录
  （`BTN_REC_BYTES`），里面把四个关节的增量各压成 8 位有符号数
  （`BTN_ANGLE_UNIT` = 0.5 度/单位，字段范围 ±127 单位 = 每周期最多 ±63.5 度）。
  **不动也要写一条全零记录**，所以回放的时间轴就是录制时的时间轴。超出 8 位字段的
  增量会被夹紧，多出来的部分由 `s_snap[]` 顺延到后面几个周期：总位移仍然精确，
  只是很快的动作会在回放时晚一两个周期到位。字段宽度是按"最快的一档"选的：
  ±63.5 度 / 200 ms = **±317 度/秒**，只有快速档（`setSpeed(2.0, 5, 20)`，最快
  400 度/秒）才会碰到夹紧。
  缓冲 `WEARM_REC_ENTRIES` = **192 条 × 4 字节 = 768 字节 SRAM**，即单次录制上限
  **38.4 秒**（`192 × 200 ms`）；写满置 `s_recOverflow` 并自动收尾，按"不合格"丢弃
  （回 `DISCARD`）。
- **回放子步**：每条记录在回放时被拆成 `BTN_PLAY_SUBSTEPS` = 4 个 50 ms 子步线性
  展开（`btnPlaySub()`），不会"200 ms 跳一格"；总时长仍等于 `s_recLen × 200 ms`，
  预摆 + 播放的耗时与录制时长同量级（探针 [5] 实测 13.02 s = 11.6 s + 1.5 s）。
- **收尾增量**：结束录制时会把积压的尾巴**排空**（`btnStopRecording()` 里最多 8 次
  `btnRecCollect()/btnRecPut()` 循环，直到没有新增量或缓冲写满），而不是只补一条。
  不做这一步，回放终点会停在最后一个整周期上 —— 四关节同时全速时积压正好一个周期的
  位移（200 ms × 100 度/秒 = 20 度），实测末态差 10~13.5 度，见教训 22。
- **按键3 播放**：先用 `BTN_RAMP_MS` = 1500 ms 在关节空间线性预摆到录制起点，
  再按录制时的时间轴复现，结束回空闲。没有录制时回 `PROTO_RES_PLAY_NO_RECORD`=16。
- **按键4 回中**：目标角由 `constant_and_positions.cpp` 新增的
  `bool posGetHomeAngles(SER *ser)` 对 `POS_HOME`（40,0,0）反解得到（`b/r/c` = 90/90/90），
  **angle4 保持当前值不动**；同样是 1500 ms 插值而不是瞬间跳变。探针直接拿这个函数
  当期望值，避免在探针里抄死 90。
- **忙与让位是两套语义**（这是本模块最容易写错的地方）：
  - `buttonControlBusy()` = 录制/播放/回中任一 → 串口动作指令（除调速与 N/R/P/M）被挡。
  - `buttonControlLocked()` = 播放/回中（**不含录制**） → 摇杆让位。
  - 忙守卫必须**豁免 N/R/P/M 本身**，否则录制中发 `R` 想结束录制会被自己的忙守卫吞掉
    （probe_button 专门有一条用例守着这个）。
- **新增返回值**：12 录制开始、13 录制已保存、14 录制被拒、15 播放开始、
  16 无可播放录制、17 回中开始（都定义在 `serial_protocol.h`）。

## 新增绘图功能（铅笔绘制，v1.0.0）

本轮新增 `draw_control.h` / `draw_control.cpp`：机械臂末端夹一支铅笔，在纸面上画图。
**接口、状态机、几何全在这一个 `.cpp` 里**，其它模块只加了一行转交。

- **纸面坐标系**：默认纸面高度 `z = -20.0` —— 初始位姿末端是 `(40,0,0)`（完全伸直的姿态，见"初始
  位姿改为 (40,0,0)"一节），铅笔是**刚性**固定在夹具上的，纸面只有落在初始位姿**下方**才可能被笔尖碰到，
  所以默认取 `-20.0` = 初始位姿再往下 20 单位（1 单位 = 4 mm，即铅笔露出约 80 mm）。
  （v1.6.6 之前这里写作 `-12.0`——那是把老模型的 +12 直接取负号得到的，物理上等于"纸面比待机
  高 8 单位"，笔尖永远碰不到纸，还会让"抬笔平移全程高于纸面"的自检失败。）
  内置图形的中心 `(27,0)`、半宽 `6`（顶点落在 ±半宽 的正方形里 → 默认 x[21,33] y[-6,6]）。
  三个量都能标定：串口 `p<纸面高>` / `n<半宽>` / `o<x>,<y>`；半宽与中心仍按各自区间拒绝
  越界值，**纸面高度已取消范围限制**（只拒 NaN，见文末"删除夹爪范围限制"一节）。
- **任务与阶段**：任务号 0 直线 / 1 字母N / 2 三角形 / 3 字母Z / 4 字母V / 5 五点折线 / 6 五点曲线
  （默认直线，串口 `F` 循环切换，每换一次回一行 `OK F=<模式>`，模式标签见 `drawTaskTag()`：
  `LINE/N/TRI/Z/V/POLY/CURVE`；原来的 字母N / 三角形 / 字母Z 曾在分支 draw_control 里
  为省 flash 删掉，现已按题目"从 N/三角形/Z/V 里选一种、同组不得完全相同"的要求全部恢复）。
  阶段 `IDLE→HOME→TRAVEL→PLUNGE→PATH→LIFT→RETURN→IDLE`，
  示教任务先 `HOME→TEACH→TEACH_WAIT→HOME→…`。
- **抬笔/落笔高度**：`DRAW_LIFT_DZ 4.0`；`liftZFor()` 若"纸面 +4"不可达就每次降 0.5
  直到可达（避免在小臂展区域直接判失败）。**抬笔阶段必须整段高于纸面**，
  否则平移时笔尖会在纸上拖出一道多余的线（probe_draw 有一条专门守着）。
- **速度**：笔尖线速度上限 `DRAW_V_MAX 3.0` 单位/秒，梯形加减速（`DRAW_ACCEL 6.0`），
  关节角速度硬上限 `DRAW_MAX_DPS 70.0`（超限就拒绝这一步，由调用方减小步长）。
  **分支 draw_control 把它们整体放慢**（原 8.0 / 12.0 / 110.0），并且 `pathTick()`
  每一轮最多只送出 `DRAW_STEP_MAX 0.02` 单位的位移（正常 loop 周期下算出来的步长
  本来就只有 0.003~0.015，这个上限只在 loop 被拖长时才生效）
  （probe_draw 实测相邻两步最大 0.015 单位）。
- **路径校验**：复用 `pick_place.cpp` 的 `solveJoint/pointOk/segmentOk` 思路
  （`DRAW_PATH_SAMPLE_STEP 0.25`（本分支由 0.5 收紧）、最多 96 采样、相邻采样反解跳变 ≤ `25°` → 换分支就判这条直线不能走）。
  五点折线与曲线在启动前先把"待机位→起点上方→垂直落笔→轨迹本体→终点抬笔"整条路校验一遍，
  失败就回 `PROTO_RES_DRAW_REJECTED` 且 `Pos` 一个字节都不动。
- **曲线**：向心 Catmull-Rom（节点间距取 `sqrt(|dP|)`，端点用弦方向切线），
  逐段 64 采样求弧长后按弧长匀速走，所以"平滑"不是靠调参而是几何决定的
  （probe_draw 实测每 5 ms 最大转角 0.38°、相邻采样最大间距 0.015）。
- **五点示教**：`TEACH` 阶段由本模块**自己读摇杆**做**笛卡尔点动**
  （A0→x、A1→y、A3 前推→z 下降；**A2（夹爪）默认整路不响应**，见"示教摇杆点动修复"一节），
  按键1 记录（5 点记满自动开始，也可按键4 手动开始）、
  按键2 撤销、按键3 取消。记录的点就是 `Pos.rec`，绘制时按这些点连线/插值。
  每格位移按偏转比例在 `DRAW_JOG_STEP_MIN 0.02 ~ DRAW_JOG_STEP_MAX 0.25` 工作区单位之间缩放，
  步进间隔是**固定的** `speed.stepDelayMs`（慢/中/快 = 80/40/20 ms）——
  只有步长按偏转缩放，节奏对任何偏转都一样；"偏转越大间隔越短"的插值已在
  v1.6.4 第二轮（依据 m15921）整段删除，见本文末的"摇杆手感修正"一节）。
- **过点判定**：`pathTick()` 里当已走过的弧长越过第 i 个点的弧长位置时才量距离，
  `<= DRAW_POINT_TOL 0.8` 记为该点命中（`drawLastPointsHit()`）。
- **按键分工（按阶段自动切换语义）**：示教中 1=记录 2=撤销 3=取消 4=开始；
  绘制中 1=暂停 2=继续 3=取消；空闲时四个按键仍是原来的循环取放/录制/播放/回中。
  转交点只有一行：`button_control.cpp` 的 `btnAction()` 开头
  `if (drawAcceptButton(key)) return drawHandleButton(key);`。
- **暂停/继续/取消**：暂停只是置 `s_paused`（阶段与已走弧长都保留，笔尖一动不动）；
  继续清暂停并把速度清零重新加速（**从暂停处接续，不会从头重画**）；
  取消先**垂直抬笔**再回待机（`drawCancel()` 里那行 `s_phase = DRAW_PHASE_LIFT;`
  千万不能漏，见教训 24）。
- **串口**：`F` 换任务 / `D` 开始 / `G` 记录 / `E` 撤销 / `Q` 暂停 / `U` 继续 / `W` 取消，
  标定 `p`/`n`/`o`；新增返回值 **18~26**（任务已选/已开始/已暂停/已继续/已取消/示教点已记录/
  示教点已撤销/被拒/已标定，定义在 `serial_protocol.h`）。
- **三方互斥**：绘图与"取放序列""按键录制/播放/回中"互斥（`drawControlBusy()` 进串口忙守卫，
  `drawControlLocked()` 让摇杆整段让位）；**绘图命令本身必须豁免忙守卫**，
  否则"绘制中想暂停"会被自己的忙守卫吞掉（和 N/R/P/M 同一个坑）。
- **卡死保护**：连续 `DRAW_STALL_LIMIT 500` 轮没能让状态前进（关节速率或可达性受限），
  就退回空闲并打印原因，不会永远停在某个阶段。

## v1.1.0 —— Uno 容量压缩与配置开关

**问题**：v1.0.0 把取放、四按键、绘图三套功能全编进同一个固件，Arduino IDE 直接报

    Sketch uses 51452 bytes (159%) of program storage space. Maximum is 32256 bytes.
    Global variables use 2319 bytes (113%) of dynamic memory, leaving -271 bytes for
    local variables. Maximum is 2048 bytes.
    Sketch too big; ... text section exceeds available space in board

**结论**：逐函数压过一轮之后，三功能同时编进去是 **32842 B / 1163 B**
（比 v1.0.0 小 36%，其中 SRAM 从 2319 B 降到 1163 B，早就不超了），
但 **flash 仍然差 586 B**，所以 v1.1.0 的出厂默认只开「取放 + 绘图」两功能
（29476 B / 638 B），四按键在 `weArm_config.h` 里把 1 个数字改回 1 就能换回来。

### 第一步：把调试日志关掉（−9260 B）

`weArm_config.h` 的 `WEARM_DEBUG_SERIAL` 默认 0。六个模块各自的中文
`Serial.print(F("..."))` 日志加起来 **9260 B**（51452 → 42192）。
顺带纠正 v1.0.0 注释里的一个错误说法：**AVR 的 `.rodata` 是并进 `.text` 的
（`avr-size -A` 实测），字符串常量只在 flash 里，不占 SRAM**；
真正让 SRAM 涨的是 `button_control.cpp` 那个 1024 B 的录制缓冲和一堆 `static` 表。

同时把「必须保留的应答」和「可删的调试明细」拆成两级开关：
`WEARM_DEBUG_SERIAL`（明细，默认 0）与 `WEARM_SERIAL_RESPONSES`（`OK`/`REJECTED`
这类应答，默认 1）。v1.0.0 里所有 `Serial.print` 都被 `#if WEARM_DEBUG_SERIAL`
包着，**一旦关调试整机就变成哑巴**——开机没有任何输出、任何命令都没有回显。

### 第二步：逐函数压缩（42192 → 32842，−9350 B）

一轮一轮实测出来的，按收益从大到小：

- **合并三个模块重复的几何核心**（−936 B）：`pick_place.cpp` 与 `draw_control.cpp`
  各自有一份 `solveJoint` / `pointOk` / `segmentOk` / `setJoints`，LTO 已经把
  它们复制成 2~3 份（`lto_priv.*`）。抽到新文件 `path_core.h`，用
  **非 static 的 `inline`**（走 COMDAT，链接器保证只留一份），
  `draw_control.cpp` 保留同名转发函数，调用点一行不用改。
- **`constant_and_positions.cpp`**（−542 B）：`getAngleEx` 去掉冗余的候选角枚举
  （2530 → 2040）；删掉整个 `applyJointLimits` 与它的备份/回滚——进函数前
  angle1..3 已被**同样容差**的区间判断筛过，"微小负角归零"只会把角推向区间内部，
  于是只需要判 angle4 并且在写 `Pos.ser` **之前**返回 false，回滚自然就不需要了。
- **`move.cpp` + `joystick_control.cpp`**（−814 B）：改为"副本试算、全通过才提交"；
  6 个 `switch` 分支折成 PROGMEM 打包表 `DIR_CODE[7]`；`posOutOfRange`/`samePose`
  改成 3 轴循环与逐位比较；摇杆的浮点比例夹取改成整数夹取。
- **`serial_protocol.cpp`**（−86 B）：`protoHandleLine` 的 19 路 `switch` 换成
  `if/else` 链——原来 GCC 会生成 64 项 `.rodata` 跳表 + 24 位范围检查 + `_tablejump2`。
  这个文件里很多"看起来能省"的写法实测是**变大的**（例如给 `protoFlushLine`
  加 `noinline` 反而 +150 B）。
- **`button_control.cpp`**（−264 B）：录制缓冲从 512 × 2 B 的 `(code, arg)` 条目
  改成 **128 × 3 B 的打包记录**（每 100 ms 一条，四个关节的 6 位有符号增量、
  0.5° 为单位），`s_buf` 从 1024 B 掉到 384 B；单次录制上限 12.8 s
- **`draw_control.cpp`**（−2020 B）：5 张图形表进 PROGMEM；`s_segLen[5]` 删掉
  （弧长现算）；`curveSpan` 从 2398 B 压到 1470 B；状态变量收窄成 `int8_t`。
- 常量表一律 PROGMEM，但注意：**这只能省 SRAM，省不了 flash**——
  `.data` 的初值本来就在 flash 里有一份（`Program = .text + .data`），
  搬进 `.rodata` 还是那一份，只是不用再拷进 RAM。

### 为什么三功能不再挤一挤（剩下的 586 B 在哪）

最大的一笔"外部"开销是 **Arduino 的 `Serial` 栈：实测 1014 B flash / 181 B RAM**。
量法：同一个最小 sketch，只做 4 个 `Servo` 的 `attach`/`write` 是
Program 1876 / Data 63，再加一句 `Serial.begin(115200); Serial.print("boot");`
就变成 2890 / 244（两个 sketch 留在
`.selfcheck/out/probe/a_noserial/sk.ino` 与 `.selfcheck/out/probe/b_serial/sk.ino`）。
另外 `Serial`/`Servo` 的全局对象还有 202 B 的构造代码（`_GLOBAL__I_...`），
反汇编看就是库自己的 `servo_info[]` 注册循环。

也就是说，要再挤出 586 B 只剩"把 `Serial` 换成裸 UART 寄存器读写"这一条路。
它要重写 `begin/print/println/write/available/read/flush` 一整层、
自己管接收中断，属于**在硬件通信这个最不能出错的地方动刀**，
不适合放在一个"修编译错误"的版本里，所以 v1.1.0 不做，如实记录在这里。

**本轮把这条路走通了**（详见下一节）：省 852 B flash / 109 B SRAM，
三功能全开 32842 → 31936 B，**默认配置就是全功能**。

顺带发现但**没有采纳**的几个写法（实测不划算或不等价）：

- `-Wl,--relax` 能再省 400 B 出头，但要用户在 `platform.local.txt` 里加链接参数，
  默认编译享受不到，所以不作为交付方案。
- `constant_and_positions.cpp` 里只剩一处 `acos`（`acos(cosC)` 消分支用），
  删掉能省 100~150 B，但改写会动到反解的数值，而探针对反解残差很敏感。
- 位折叠命令分派（`'M'/'N'/'P'/'R'` 折成 0/1/2/3）看着能省几十字节，
  实测**直接打断功能**：那四个字符的差值其实是 0/1/3/5，`'R'` 会被判成未知命令，
  串口再也结束不了录制。这一处已经在 `button_control.cpp` 里加了警示注释。

### 怎么选配置

改 `weArm_config.h` 里三个数字即可（0 = 关，1 = 开），别的文件都不用动：

    WEARM_ENABLE_PICK_PLACE   取放序列（串口 A/B/C、按键1 循环取放）
    WEARM_ENABLE_BUTTONS      按键模块（录制/播放/回中/循环取放，串口 N/R/P/M/0）
    WEARM_ENABLE_DRAW         绘图（铅笔轨迹）
    WEARM_BUTTON_PINS         0 = 不读 D2~D5 的物理按键（本轮起的默认值）
                              1 = 四个独立按键接 D2~D5（INPUT_PULLUP、按下接地）

关掉的功能会被链接器整段丢掉（头文件里退化成空 inline 桩），
命令行 `-D` 依然可以覆盖本文件的默认值。
**v1.1.0 时默认是「取放 + 绘图」，四按键关着；本轮起三个功能开关默认都是 1**
（见下一节）。但**物理按键默认不读**：本机 D2~D5 上没有独立按键，只把摇杆自带的
SW 脚接到 D2，而右摇杆推到最前会压合那颗轻触开关、假触发"按键1 循环取放"，
所以 `WEARM_BUTTON_PINS` 默认 0，四个功能全部走串口字符
（`N` 循环执行 / `R` 录制开关 / `P` 播放 / `M` 或 `0` 回中）。
详见"上机才能确认"第 7 条。

**注意**：`mock/Arduino.h` 为配合 `draw_control.cpp` / `pick_place.cpp` 的
`PROGMEM` 常量表，新增了 `pgm_read_byte/word/dword/float/ptr`；
因为 PC 上 `double` 是 64 位而 AVR 上就是 32 位 float，`pgm_read_float`
在 mock 里直接按 `double` 读，才能让两端算出一模一样的结果。

### 两个新踩到的坑

1. **LTO 偶发 `lto1.exe: internal compiler error: resolution sub id ... not in object file`**：
   换一个全新的 `-BuildRoot`（清掉 `core.a` 之外的中间 `.o`/`.ltrans`）重试即可，
   是 avr-gcc 7.3.0 的 LTO 缓存问题，不是代码问题。
2. **写完新构建目录记得先更新 `.gitignore`**：`avr_build.ps1` 默认的
   `-BuildRoot` 是 `.selfcheck/avrbuild`，`git add -A` 会把 `core.a`
   和几十个中间文件一起提交进去。

## 角度语义回归 / 七任务恢复 / 与任务无关代码删减（当前版本）

这一节描述**现在**的行为，优先级高于下面任何历史章节（凡与本节冲突的，
以本节为准；冲突章节都加了 ⚠ 作废标注）。

### 1) 串口 `x/y/z` = 三个舵机的角度（不是末端坐标）

题目的例子是 `x10,y30,z20`，要求"三个指定舵机的 PWM 占空比同步改变"，所以
`x/y/z` 直接映射到三个关节角，**不做逆解**：

| 轴 | 舵机 | `Pos` 成员 |
| --- | --- | --- |
| `x` | 基座 b | `Pos.ser.angle1` |
| `y` | 上臂 r | `Pos.ser.angle2` |
| `z` | 下臂 c | `Pos.ser.angle3` |

- 解析：`protoParseAxisLine()`（接受大小写、空格、`x=20`、小数、只给一部分轴）
- 落地：`protoApplyAngles()` —— 把提到的轴写进 `Pos.ser.angle1..3`，
  再 `clampServoAngles()`（按舵机电气行程 0~180 夹取，**夹取而不拒绝**，保证位姿有定义）
  与 `recFromServo()`（正解刷新 `Pos.rec`，保持"关节角是唯一真值"）
- 回复：成功 `OK`（`PROTO_RES_ANGLES_SET`）；语法错 `ERR`；忙时 `BUSY` 且状态零改动
- `x200` 这类超行程值会被夹到 180（`180.0`），不会静默丢掉

### 2) 绘图任务表回到 7 项，并回报当前模式

`LINE 0 / N 1 / TRIANGLE 2 / Z 3 / V 4 / POLYLINE 5 / CURVE 6`；
`drawTaskTag()` 给出 ASCII 短标签 `LINE / N / TRI / Z / V / POLY / CURVE`，
串口 `F` 换任务时回一行 `OK F=<tag>`（例如 `OK F=TRI`），
`WEARM_DEBUG_SERIAL=1` 时另打印中文名。

### 3) 删掉的代码（与题目无关或已无调用点）

| 符号 | 原因 |
| --- | --- |
| `moveAxisStep()` | 只是 `moveJointStep()` 的转发，无调用点 |
| `joystickGetMode()` / `JOY_MODE_VERT` / `JOY_MODE_COUNT` | 恒返回 `JOY_MODE_PLANE`，无调用点 |
| `atRangeEdge()` | 边界判定，无调用点 |
| `posToolOpen()` / `posToolClose()` | 只被串口 `k/K` 使用 |
| 串口 `1/2/3` | 档位直达，题目只要求 `H/L` 升降档 |
| 串口 `k/K` | 末端步进开合，题目只要求 `O/S` 全开全关 |
| `protoAxisServoIndex[]` | 无调用点（轴→舵机的映射直接写成 `angle(a+1)`） |
| `PROTO_RES_COORDS_REJECTED` | 坐标语义专用，逆解路径已删 |
| `WEARM_SHOULDER_HEIGHT` | 坐标语义专用 |

对应地，结果码 `5`（原 `1/2/3`）留空，`6` 改为 `PROTO_RES_FEATURE`
（`!` / `!P` / `!B` / `!D` 的返回值），12~26 一律不动以免牵动探针与文档。

## 本轮改动 —— 地面坐标系指令 / 全功能默认开启 / 裸 UART 后端 / 失败回复分级

> **⚠ 本章第 1 节已作废**（v1.6.4 起）：串口 `x,y,z` 又改回"直接写三个舵机的角度"
> —— 题目给的例子是 `x10,y30,z20`，要求三个指定舵机的 PWM 占空比同步改变，
> 逆解出来的中间量反而对不上题。地面坐标系版本保留在分支 `backup/xyz-cartesian`
> （= tag `v1.6.3`）与 `dist\meArm_xyz_cartesian_v1.6.3_source.zip`。
> 下面这一节只作为历史记录保留，**不要照它理解现在的串口语义**；
> 现行语义见"角度语义回归"一节。

三个目标：把串口 `x,y,z` 从"直接写关节角"改成**地面坐标系下的末端点**；
让串口 `R` 不再动辄回一行含混的 `REJECTED`；把三功能全开压进 Uno 并设为默认。

### 1) `x,y,z` 改成地面坐标系（**破坏性变更**）

坐标系按题目要求：**原点 = 过肩关节的地面垂线的垂足，x 轴 = 机械臂初始面朝
方向，z 轴 = 垂直地面向上**（右手系，+y 在初始面朝方向的左手边）。

内部坐标本来就已经是同一套：`constant_and_positions.cpp` 的 `recFromServo()`
里 `theta = (90 - b)/RADtoDEG; x = xPlanar*cos(theta); y = xPlanar*sin(theta)`，
b = 90° 时朝 +x、b < 90° 时转向 +y，所以两套坐标只差 **z 的原点**：

    z_内部 = z_地面 − WEARM_SHOULDER_HEIGHT

`WEARM_SHOULDER_HEIGHT` 新增在 `constant_and_positions.h`，默认 **20.0**。
20 不是拍脑袋来的：内部 z 的下限原本就是 `limit.minZ = −20`，把地面定在 −20，
可达范围正好变成 **z ∈ [0, 60]，且反解不会算到地面以下**。真机肩高不同就改这一个常量。

语法没变（`x20,y0,z40`，也接受 `x=20` 和只给一部分轴），但含义彻底变了：

- 旧：`x10` = 基座关节转到 10°
- 新：`x10` = 末端水平位置 x = 10，再由 `getAngleEx()` **反解**成四个关节角

因此**不可达的点会回 `REJECTED`**（旧实现是照写关节角，"写不进去"也不吭声）；
只给 z 轴时另外两个轴沿用当前末端位置，等价于"竖直平移"。

### 2) 串口回复分级（不再只有 OK / REJECTED）

| 回复 | 含义 |
|---|---|
| `OK` / `OK #` | 已执行（`O`/`S` 会带上夹爪当前角度；`F` 换任务回 `OK F=<tag>`） |
| `BUSY` | 命令认识，但取放/录制/播放/绘图正在跑，先让位 |
| `OFF` | 该模块**编进了固件**，但被 `!P` / `!B` / `!D` 在运行时关掉了 |
| `DISCARD` | `R` 结束录制，但这段录制不合格（太短/没有位移/溢出），已丢弃 |
| `EMPTY` | `P` 想回放，但根本没有录制数据 |
| `ERR` | 语法错（例如 `!` 后面跟了不认识的功能字母） |
| `REJECTED` | 固件里**没有**这个模块，或（关闭的模块收到绘图/取放命令）轨迹校验不过 |

`R` 之前"一输入就 REJECTED"是两层原因叠出来的：v1.1.0 出厂配置把四按键
（`WEARM_ENABLE_BUTTONS`）关掉了，按键命令在门控处直接回 `REJECTED`；
而录制"太短/没位移"也回同一个 `REJECTED`。现在默认全功能，且原因分开报。
记住 `R` 是**两段式**：第一次 R 开始录制（回 `OK`），第二次 R 结束并校验
（回 `OK`，或 `DISCARD` 表示这段不要了）。`P` 没有数据时回 `EMPTY`。

### 3) 运行时功能开关 `!`

- `!` 查询当前状态，回一行 `P=1 B=1 D=1`（1 = 启用，0 = 已关闭）
- `!P` / `!B` / `!D` 切换取放 / 按键 / 绘图；未编进固件的模块回 `REJECTED`

语义边界（别误解）：

- 只影响**串口分发**。关掉 `B` 之后（在 `WEARM_BUTTON_PINS=1` 接了实体按键的
  机器上）实体按键照样能用，正在跑的任务也不会被中止
  （本机默认 `WEARM_BUTTON_PINS=0`、没有实体按键，所以关掉 `B` 就是这四条命令
  `N/R/P/M/0` 全部回 `REJECTED`，见"本轮改动"第 7 节）
- 只能关掉"已经编进固件"的模块；编译期裁掉的功能永远回 `REJECTED`
- 上电时运行时状态 = 编译期状态（`serialProtocolBegin()` 里重置）

### 4) 裸 UART 后端：省下 852 B flash / 109 B SRAM

`serial_protocol.cpp` 新增 "serial backend" 一段，release 的 AVR 构建不再使用
Arduino 的 `HardwareSerial`：

- 发送：`while (!(UCSR0A & (1<<UDRE0))) {} UDR0 = c;`
- 接收：`ISR(USART_RX_vect) { protoRxStore(UDR0); }` 填 64 字节 2 的幂环形缓冲，
  主循环用 `protoRxTake()` 取字节（空返回 −1），`serialProtocolLoop()` 的读取循环
  改成 `while ((c = protoRxTake()) >= 0)`
- 初始化照抄 core 的算法：`UCSR0A = 1<<U2X0`、
  `UBRR = (F_CPU/4/PROTO_BAUD − 1)/2`（16 MHz + 115200 → 16）、
  `UCSR0C = 8N1`、`UCSR0B = RXEN0|TXEN0|RXCIE0`

**为什么必须整层换而不是逐个函数裁**：只要链接了 `Serial` 对象，它的 vtable 就会
把 `HardwareSerial::write/_tx_udr_empty_irq/flush/available/read/peek`、
`Print::write`、`__vector_18/19`、`serialEventRun` 甚至 157 B 的 `Serial` 对象
全部拖进镜像（实测清单见 git 历史里的 `avr-nm` 输出），逐函数裁剪做不到。

退路：`-DWEARM_SERIAL_ARDUINO=1` 强制用回官方串口库；`WEARM_DEBUG_SERIAL=1`
和 PC 端 mock 构建也自动走原来的 `Serial` 路径（调试日志与协议回复要共用一条
有序输出流，探针语义因此完全不变）。

**这一层是唯一没法在 PC 上验证的部分**（中断和寄存器只在 AVR 上存在）：
环形缓冲的推入/取出、`USART_RX_vect`、寄存器初值都不在 mock 的覆盖范围里，
PC 探针只能证明"改用 `protoRxTake()` 之后 mock 路径的行为没变"。
所以上机第一件事就是确认 115200 baud 下收发正常（见文末"上机才能确认"）。

### 5) 本轮容量矩阵（实测）

|---|---|---|---|---|
| 取放 + 按键 + 绘图（**本轮默认**） | 31936 | 97.5% | 1015 | 49.6% |
| 取放 + 绘图（按键关） | 28534 | 87.1% | 490 | 23.9% |
| 取放 + 按键（绘图关） | 19226 | 58.7% | 807 | 39.4% |

    powershell -NoProfile -ExecutionPolicy Bypass -File .selfcheck\avr_build.ps1 `
        -ExtraDefs @('-DWEARM_ENABLE_BUTTONS=0')

`avr_build.ps1` 已不再编译 Servo 库（换成自研 `servo_drive.cpp`），
mock 侧的 `mock/Servo.cpp`、`mock/Servo.h` 也已删除。

### 6) 新增/改动的探针

`probe_protocol` 的"串口应答与运行时功能开关"一段（12 段）**移到了压力测试之前**：

> 压力测试会随机发单字符 `'A'..'Z'`，其中 `A/B/C` 会启动取放序列，
> 而 `pickPlaceIsBusy()` 是 `s_obj >= 0`，一旦启动就再也不会回到空闲 ——
> 后面的 `R` 只能回 `BUSY`。所以应答测试必须先跑，并以"结束录制"收尾。

新增断言：`!` 回 `P=1 B=1 D=1`；`!P`/`!B`/`!D` 往返切换；
`!B` 关掉后 `N` 回 `OFF`（且输出里不能出现 `REJECTED`）；
录制中发 `O` 回 `BUSY`；立刻结束录制回 `DISCARD`；没有数据时 `P` 回 `EMPTY`。

**教训**：探针用 `-DWEARM_DEBUG_SERIAL=1` 编译，mock 的输出流里既有中文调试日志
又有协议回复，断言只能查"回复这一行在不在"
（`out.find("OK\n") != std::string::npos`），**不能整串相等**。

## 本轮改动 —— 四个实机问题的修复（方向 / 无故乱动 / 录完按 P 报 busy / 注释）+ 物理按键停用

现场反馈四条：①左右旋转的舵机转向反了、抓取时 `O`/`S` 反了；②机械臂经常无故乱动；
③录完动作再输入 `P` 触发 `BUSY`、录的动作执行不了；④注释与实现不符。
之后又追加一条：⑤右摇杆向前本该转下臂，却触发了自动取放 —— 见第 7 节。

### 1) 基座与夹爪的方向镜像（问题 ①）

根因是**装配**：这台机器的基座回转（通道 0 / b）与末端夹爪（通道 3 / f）的舵机是
反向装上的，逻辑角增大时它们物理上朝反方向走。`O`（逻辑角 150）本该张开、实际夹紧，
就是同一个原因（不是 `O`/`S` 写反了）。

修法**不动 0~180 映射、也不动任何逻辑角**，只在唯一写出口 `meArm.ino` 的
`writeServo()` 里对这两个通道做一次镜像：

    physical = mirror_sum - logical      /* ch0（基座）mirror_sum = 180（整行程对称）
                                            ch3（夹爪）mirror_sum = TOOL_MIRROR_SUM = 210 */

**上臂/下臂（ch1/ch2）默认不镜像**：`weArm_config.h` 里 `WEARM_MIRROR_SHOULDER` /
`WEARM_MIRROR_ELBOW` 的出厂值都是 0，因为这两个舵机是**正向装配**的，正解
`alpha = 90° - r`（`beta = c - 90°`）本身已经把"逻辑角增大 = 竖直方向反向"算了进去。
把 ch1 置 1（`physical = 180 - r`）时 `cos(90°-r)` 不变而 `sin(90°-r)` 取反，于是
**水平分量不变、上臂的竖直分量整体反号** —— 真机症状恰好是"上下搞反、其余正常"。
上机标定时可在串口用 `m` 查询、`mS` 切换上臂、`mE` 切换下臂（运行时值，掉电不保存），
选对之后把结果回写到 `weArm_config.h` 的两个宏。

限位、反解、录制回放、绘图示教全都继续用逻辑角（唯一真值），变的只是最后送到舵机的
那个数。**注意**：夹爪的镜像和 210 是按"名义窗口 60~150"标定的；后来夹爪逻辑角范围
放宽到 0~180（见文末"删除夹爪范围限制"一节），镜像后的物理角就可能超出 0~180
（逻辑 0 → 物理 210），由 `servo_drive` 在脉宽层面夹到电气行程端点。开关在
`weArm_config.h`：`WEARM_MIRROR_BASE` / `WEARM_MIRROR_TOOL`（换回正装装配就置 0）。

> **注意副作用**：基座镜像之后，所有含 `±y` 的笛卡尔目标点都会落到**镜像侧**
> ——`pick_place.cpp` 顶部的 `PICK_SRC`/`PICK_DST` 正是这种点。若上机发现 A/B/C 去
> 了反方向，那说明这些常量是按"反装基座"标定的，把它们的 `y` 取反即可
> （或直接把物体摆到镜像侧）。这一条列进了文末"上机才能确认"。

### 2) 摇杆中位自标定（问题 ②）

`JOY_CENTER` 是硬编码 512、死区只有 15 个计数，而真实双轴手柄的机械中位常见偏
20~60 个计数。偏 20 就已经越过死区 ⇒ 手不碰摇杆时每一路都被当成"轻微推杆"，
每过一个时间门就步进一次 —— 机械臂持续缓慢地自己乱走。这是"无故乱动"最可能的
软件侧原因。

修法：`joystickSetup()` 里四路各平均 `JOY_CAL_SAMPLES` 次，把相对 512 的静态
偏差存进 `s_centerOff[]`，`readAxisAmp()` 读到的值先扣偏差再算死区与方向
（下游所有 `raw > JOY_CENTER` 判断因此一行都不用改）。偏差超过
`JOY_CAL_MAX_OFF` 判为"标定时手正压着摇杆"，退回 0（宁可回到老行为，也不把
一路轴标歪）。`probe_joystick` 的 [9] 段测这一套：偏 +70 静止 30 轮必须一动不动、
偏置之上推杆方向仍然正确、偏 +100 不采纳、标准 512 与历史行为一致。

> **v1.6.4 加强（见文末"摇杆手感修正"）**：`8 → 32` 次平均、`64 → 80` 上限、
> 死区 `15 → 40`，并新增**运行期中位跟踪**：当某一路偏差落在起控门槛以内时，把它的
> 静态偏差朝当前读数挪 1 个计数（第二轮起加了 `JOY_TRACK_MS 20` 时间门控，
> 否则 20kHz 级的主循环十几毫秒就能把几十个计数"追"成假中位）。
> 同一段还有 [10] 回归：每轮漂移 +1 共 +110 计数，关节必须一动不动。
> **第二轮（m15921）**又加了**施密特迟滞**：静止时要跨过 `40 + JOY_HYST 25 = 65` 个计数
> 才起控，起控后门槛回落到 40 —— 41~64 这一段残余偏差既不步进也不被当成推杆，
> 正是"大臂自己一小格一小格往前抽"的直接原因。
> **已知残余隐患**：某路机械中位偏差若 > `JOY_CAL_MAX_OFF 80`，标定会整体放弃
> （偏差记 0），残余偏差 ≥ 65 仍会被当成推杆而持续步进（此时跟踪因"已起控"不介入）。
> **更一般地**：只要偏差冲过 65 起控门槛，跟踪就再也不介入（这是有意的——起控后还跟踪
> 会把真实操作吃掉），所以这一段只能靠调大 `JOY_DEADZONE`/`JOY_HYST` 或重新上电标定
> 来兜；41~64 这一段才是本轮迟滞真正覆盖的范围。
> 缓解办法：把摇杆装正、或把 `JOY_CAL_MAX_OFF` 提到 120、或长按一次重新上电标定。

### 3) 录制中直接按 `P` / 按键3：先收尾再播放（问题 ③）

旧 `btnActionPlay()` 第一句就是"录制中 → `BUSY`"，而录制只能由"结束录制"
（按键2 / 串口 `R`）停掉；用户按播放时心里已经是"我录完了"，于是永远收到 `BUSY`。

现在改成：录制中按 `P` 先调用一次 `btnStopRecording()` 收尾 —— 合格（末端有明显位移）
就紧接着播放，不合格（没动 / 缓冲溢出）就如实回 `DISCARD` 让他重录，
不再是含糊的 `BUSY`。`probe_button` 新增 [11] 段覆盖这两条路径，并断言回放终态
等于"按 P 那一刻"的位姿。

> 顺带确认两件事：①缓冲是 **192 条 × 200 ms = 38.4 s**（4 字节/条），再长的录像会写满
> 溢出（回 `DISCARD`）；②**"录制时长必须 >10 s"这条最下限于本轮删除**（见 `button_control.h`），
> 所以现在 1 秒的动作只要走够了 10 个坐标单位位移就照样保存，可用的录制窗口从
> 原来的 10.0~12.8 s 变成 0~38.4 s。`probe_button` [3] 段新增了一条
> "8.2 秒短录像只要位移够就回 `REC_SAVED`"的回归。

### 4) `servo_drive` 的注释与帧尾写法（**没有修 bug，只是把话说清楚**）

审读时一度怀疑"帧尾现算剩余量"会 uint16 下溢、把帧长变成 ~52.8 ms。**核对后确认
v1.3.0 的实现本来就是对的**：帧尾比较值是在"4 路都发完"那次中断里算的，那时
`nowTicks` 只有四路脉宽之和（默认 12000，最宽 <19184），`40000-12000` 不会下溢。
本轮只做两件事：把帧尾写成绝对常量 `*nextDelayTicks = SERVO_FRAME_TICKS;`
（与旧的 `nowTicks + remain` **逐位等价**，删掉从未触发的 40 tick 保护与 `s_phase`），
并把"为什么不能在帧尾中断里现算"这个**危险点**写进注释（将来真有人把这段挪到
帧边界分支里就会踩到）。

`probe_servo_drive` 新增带**中断延迟**的时序模型 `framePeriodTicks(latency)`：
旧模型的 `nowTicks` 恰好等于上一次排定的比较值（零延迟），验证不了真实帧长。
新用例断言延迟 2/6/30 tick 时帧间隔 ∈ [40000, 40000+8·延迟]（实测 40002/40006/40030）
且绝不接近 ~52800。

### 7) 物理按键停用：右摇杆推到最前会假触发"循环取放"（问题 ⑤）

**现象**：右摇杆向前（本应让下臂向前转）推到底，机械臂却开始自动取放。

**根因（代码侧证据）**：`joystickLoop()` 里没有任何取放/按键调用；`pickPlaceStart()`
全工程只有两个调用点 —— 串口 `A/B/C` 与 `button_control.cpp` 的 `btnActionCycle()`
（物理按键1）。所以推杆本身不可能启动取放，一定是 **D2 被拉低**。本机 D2~D5 上
没有独立按键，只把摇杆自带的按压开关（KY-023 的 SW 脚）接到了 D2 = 按键1；
推到最前时机械上会压合那颗轻触开关 → 一次假"按下沿" → `pickPlaceStart()` 抢走
正在手动推杆的操作，摇杆随即被 `joystick_control.cpp` 的 `locked`
（`pickPlaceIsBusy() | buttonControlLocked() | drawControlLocked()`）锁住 ——
现象正好是"下臂动一点就停、然后开始取放"。

**改法（固件侧，不依赖改线）**：`weArm_config.h` 新增第 4 节开关

    WEARM_BUTTON_PINS   0（默认）= 完全不读 D2~D5：buttonSetup() 不做 pinMode、
                        buttonLoop() 不扫描、btnEdge()/BTN_PIN[]/三个消抖数组
                        整段被 `#if` 裁掉（省 510 B flash / 28 B SRAM）
                        1 = 恢复四个独立按键接 D2~D5 的老接线

按键的四个功能因此全部由串口字符触发（本来就有等价命令）：

| 功能 | 串口 | 物理按键（改成 1 才有） |
|---|---|---|
| 循环执行 A→B→C | `N` | 按键1 / D2 |
| 录制 开/关 | `R` | 按键2 / D3 |
| 播放上一次录制 | `P` | 按键3 / D4 |
| 回中（POS_HOME） | `M` 或 `0` | 按键4 / D5 |

**注意**：`WEARM_ENABLE_BUTTONS` 仍然保持 1 —— 串口 `N/R/P/M/0` 走的就是这个模块，
关掉它这四条命令会一起消失。`WEARM_BUTTON_PINS` 只裁剪"读引脚"那一段。
绘图示教/绘制期间的按键语义（记录/撤销/取消/开始、暂停/继续/取消）是同一套按键编号
（`BTN_KEY_*` = `DRAW_KEY_*`），所以同样能用 `N/R/P/M/0` 触发，另有
`G/E/W/Q/U/D` 等专用命令。忙守卫对 `N/R/P/M` 与绘图命令的豁免不变。

**探针**：`probe_button` / `probe_draw` 靠模拟 D2~D5 电平测按键逻辑，所以
`run_all.ps1` 给**探针**单独加了 `-DWEARM_BUTTON_PINS=1`（`$probeCfg`），
第 1 步编译固件 TU 时仍用默认 0 —— 两条路径都会被严格编译一遍；AVR 实编走默认 0。
新增的 `probe_pins_off` 反过来，用 `-DWEARM_BUTTON_PINS=0` 编译（`run_all.ps1`
里对这一个探针单独换成 `$cfg + '-DWEARM_BUTTON_PINS=0'`），它测的就是"按住
D2~D5 也什么都不发生 + 四个功能全走串口"。**注意这四条命令 `N/R/P/M/0` 都不在
固件的单字符快速派发表里**（表里只有 `O`/`S`、`A~C`、`H`/`L`、`F`/`D`/`G`/`E`/`Q`/`U`/`W` 这些单个大写字母），
探针喂命令必须带 `\n`，否则会一直等在行缓冲里（`probe_pins_off` 的 `feed()` 已经
自动补换行，这个坑就是这么踩出来的）。

## 本轮改动 —— 录制深度改造（录得更久、采样更稀、回放插值）

要求是"**增大录制的存储空间，降低采样率**"。改动集中在 `button_control.cpp`／
`button_control.h`／`weArm_config.h`，加上 `probe_button` 的新回归：

| | 改前（v1.4.0） | 改后 |
|---|---|---|
| 采样周期 `WEARM_REC_TICK_MS` | 100 ms | **200 ms** |
| 每条记录 `BTN_REC_BYTES` | 3 字节（四关节各 6 位有符号） | **4 字节（各 8 位有符号）** |
| 缓冲条数 `WEARM_REC_ENTRIES` | 128 | **192** |
| 缓冲 SRAM | 384 B | **768 B** |
| 单次录制上限 | 12.8 s | **38.4 s** |
| 每周期最大增量 | ±16°（= ±80°/s） | **±63.5°（= ±317°/s）** |

**为什么"降采样率"不能只改一个数字**：只把 100 ms 改成 200 ms，6 位字段就顶不住了 ——
正常档（`setSpeed(1.0, 10, 40)` = 100°/s）每周期走 20°，超过 ±16° 的部分被夹紧、靠
`s_snap[]` 顺延成积压；而 `btnStopRecording()` 收尾只补写**一条**记录，积压的尾巴
（实测 20°）被直接截掉 ⇒ 回放终点比录制末态短 10~13.5°（`probe_button` [9]/[11] 的
FAIL 就是这个）。所以本轮**同时**做了两件事：

1. 字段放宽到 8 位（±127 单位 = ±63.5°/条 = ±317°/s @200 ms），正常档/中速档不再削顶；
2. 收尾从"补一条"改成**排空循环**（最多 8 次 `btnRecCollect()/btnRecPut()`，直到没有
   新增量或缓冲写满），积压多少就吐多少。

**回放插值**：200 ms 一格的回放会很顿，于是每条记录在回放时被拆成 `BTN_PLAY_SUBSTEPS`
= 4 个 50 ms 子步线性展开（`btnPlayLoad()` 幂等地装载一条、`btnPlaySub()` 贴第 k 个子步、
`btnPlayTick()` 用 `subMs = BTN_TICK_MS / BTN_PLAY_SUBSTEPS` 做**均匀**时间基准）。
总时长仍严格等于 `s_recLen × 200 ms`（探针 [5] 实测 13.02 s = 11.6 s + 1.5 s）。
设 `BTN_PLAY_SUBSTEPS = 1` 就退回"整条一次跳完"的老行为。

**探针**：`probe_button` 新增 **[12] 缓冲写满**（连续推杆录到 38.2 s 仍在录制、
条目 190/192 证明 `uint16` 计数不回绕；38.8 s 写满后自动收尾并判废、事后按 `P` 回
`EMPTY`）；[9]/[11] 的回放末态差从 6~13.5° 变成 **0.00°**。

### 录制深度改造后的容量（`avr_build.ps1` 实编）

| 配置 | Program | 占 32768 | Data | 占 2048 |
|---|---|---|---|---|
| 取放 + 按键 + 绘图（**默认**） | 31938 | 97.5% | 1414 | 69.0% |
| 取放 + 绘图（按键关） | 28756 | 87.8% | 497 | 24.3% |
| 取放 + 按键（绘图关） | 19170 | 58.5% | 1206 | 58.9% |
| 绘图 + 按键（取放关） | 29180 | 89.1% | 1380 | 67.4% |

比上一轮各 **+286~334 B flash、+420 B SRAM**（缓冲 +384 B、回放子步状态 8 个
`double` 再 +64 B，另有零头被优化掉）；**"取放 + 绘图（按键关）"一行完全不变**，
因为 `button_control.cpp` 根本没参与编译。默认配置相对 32256 B 可用 flash
**只剩 318 B**（下一轮把"移动到指定 x,y,z"合并成 `moveToPoint()` 后同一默认配置降到
**31770 B**、余量 486 B，见下一章）。想再改采样率/条数只动 `weArm_config.h` 第 5 节那两个数即可：
96 条 = 19.2 s（384 B）、256 条 = 51.2 s（1024 B，Data 81.5%、栈只剩 378 B，不建议）。

## 本轮改动 —— 绘图改调公共的「移动到指定 x,y,z」核心

要求是"**调用实现移动到指定 x,y,z 坐标的函数，重构绘图功能**"。做法：让"移动到指定
坐标"在本工程**只有一份实现**，绘图与串口都调它。

### 之前是三份

| 位置 | 函数 | 语义 |
|---|---|---|
| `draw_control.cpp`（已删） | `solveStep()` + `tryApplyPoint()` | 反解后逐轴比较，超速**整点拒绝**（轨迹跟随） |
| `draw_control.cpp`（已删） | `applyPointClamped()` | 反解后超速部分**夹到上限**（示教点动） |
| `serial_protocol.cpp`（已删） | `protoMoveToCoords()` | 反解后**一次到位**，解不出来整条拒绝（串口 x/y/z） |

三份都写着同一段"构造 `pos target = Pos` → 按 `seen` 覆盖坐标 → `getAngleEx()` →
写 `Pos` + `recFromServo()`"，只是"超速怎么办"不同。

### 现在是一份，三种策略

新的公共函数在 `move.h` / `move.cpp`：

```c
int moveToPoint(const double *goal, uint8_t seen, double maxDps, double dtSec, int mode);
```

- `goal[3]` 目标点（**内部坐标系**，与 `Pos.rec` 同一套；调用方是绘图的轨迹跟随与
  `pick_place`。串口 `x/y/z` **不经过这里**：它直接写 `Pos.ser.angle1..3`，
  再由 `recFromServo()` 算出 `Pos.rec`）；
- `seen` 位掩码（`1<<0`/`1<<1`/`1<<2`），**没提及的轴沿用 `Pos.rec` 当前值** ——
  这就是"`x10` 这种单轴命令"能工作的原因；
- `maxDps × dtSec` = 本步允许的最大关节变化（下限 0.2°）；
- `mode` 三选一：`MOVE_XYZ_TRACK` 超速整点拒绝（绘图轨迹跟随）、`MOVE_XYZ_JOG`
  超速夹取（示教点动）、`MOVE_XYZ_NOW` 不限速一次到位（串口）。
- 返回 `MOVE_XYZ_OK` 才写 `Pos`，其余情况 `Pos` **逐字节不变**（探针 [7a]/[7b]/[7g]
  用 `memcmp(&Pos, ...)` 直接守这条不变量）。

### 为什么能保证"逐位相同"

- 反解的输入一样：旧 `pathCoreSolveJoint()` 是 `pos p; p.rec.x/y/z=…; p.ser=Pos.ser`，
  新代码是 `pos target = Pos;` 再覆盖 `rec` 三个轴 —— 传给 `getAngleEx()` 的 `rec` 与
  `ser` 逐位相同。失败/被吸附的判据也照抄（`clamped` 只被 `TRACK`/`JOG` 用来拒绝，
  `NOW` 与旧的 `protoMoveToCoords()` 一样忽略它）。
- 写回去的角度一样：**旧 `tryApplyPoint()` 写的是反解结果 `abc[]`，所以新的 `TRACK`
  分支也必须写反解结果 `tgt[]`**，不能写 `cur + (tgt - cur)`（浮点上不保证逐位相等）。
  `JOG` 分支反而要用 `cur + 夹取后的增量`，与旧 `applyPointClamped()` 一致。
- `s_applyMs = millis()` 仍然只在**成功之后**才前移，调用方一行没改。
- 串口侧唯一丢掉的东西：旧 `protoMoveToCoords()` 在 `recFromServo()` 失败时打的一句
  debug 警告（那条路径本来就不可达，且只在 `WEARM_DEBUG_SERIAL=1` 时存在）。

### 探针

`probe_move` 新增 **[7] `moveToPoint()`** 共 7 条：不可达/`NULL`/未知模式 → `REJECTED`
且 `Pos` 逐字节不变；`TRACK` 超速拒绝、限内接受且**写进去的角度与独立反解结果逐位相同**
（实测需动 16.335°、上限 32.670°）；`JOG` 每步 0.200°（= 10°/s × 0.02 s）不超上限、
48 步收敛到反解结果；`NOW` 一次跳变 4.57° 到位且坐标自洽；部分 `seen` 只动被提及的轴
（y/z 偏差 0 与 3.6e-15）。其余 10 个探针（尤其 `probe_draw` 的轨迹精度/示教点动/
`probe_protocol` 的 x/y/z 拒绝语义）**一个数字都没变**，这就是"等价重构"的证据。

### 2) 放慢 + 精细化插值

| 参数 | 分支前 | 分支后 | 作用 |
| --- | --- | --- | --- |
| `DRAW_V_MAX` | 8.0 | **3.0** | 笔尖巡航线速度（单位/秒） |
| `DRAW_ACCEL` | 12.0 | **6.0** | 加减速度（单位/秒²） |
| `DRAW_MAX_DPS` | 110.0 | **70.0** | 关节角速度硬上限（度/秒） |
| `DRAW_PATH_SAMPLE_STEP` | 0.5 | **0.25** | 轨迹校验采样步长（更细） |
| `DRAW_STEP_MAX` | — | **0.02** | 单次写入的最大位移（新宏） |

`pathTick()` 在把"这一轮该走的距离"送进 `pathAdvance()` 之前加了一道上限：

```c
if (step > DRAW_STEP_MAX) step = DRAW_STEP_MAX;
(void) pathAdvance(step);
```

- **正常 loop 周期（1~5 ms）、巡航 3 单位/秒** 下算出来的 `step` 只有 0.003~0.015 单位，
  这个上限**根本不生效**，速度完全按梯形规划走（probe_draw 实测相邻两步最大 0.015 单位，
  旧版是 0.040）。
- 只有某一轮 loop 被拖长（串口打印、别的模块占时间）时才限住：那一轮少走一点，
  剩下的下一轮补上 —— 宁可慢，也不让舵机一次跳一大步。*0.02 / 5 ms = 4 单位/秒 >
  `DRAW_V_MAX`，所以巡航速度不受影响。*
- 结果：一条 12 单位的直线由 **几百个密排点**组成，舵机每步只动零点几度。

> **为什么不是"一轮里拆成多个小步循环送出"**：本工程用 `-flto -Os`，
> 把 `pathAdvance()` 放进循环里会让它无法被内联，实测**同样功能要多花 662 B flash**
> （默认配置 32336 B 已经超过 Uno 可用的 32256 B，装不进去）。
> 限一步的写法只多 32 B，效果一样：**任何一次写入的位移都不超过 0.02 单位**。
> 这一步是拿真实 AVR 构建量出来的（`.selfcheck\avr_build.ps1`），不是猜的：
> 无循环但无上限 31674 B → 加循环 32336 B（+662）→ 改成上限 31706 B（+32）。
> （后来"示教点动修复"又把这个数字降到 31656 B，见 §5。）

### 4) 这一节的注意事项

- 减速只改了"画的时候走多快"，**没有改几何、没有改校验门限**（采样步长反而更细），

- 上机确认项：慢速下舵机是否有明显抖动/异响（尤其加减速段与顶点处）；

> 这条约定整个删掉**——间隔改成与偏转无关的固定值 `speed.stepDelayMs`（慢/中/快 = 80/40/20 ms），
> 偏转只影响**每格步长**。所以现在既不是"偏转大 = 快"也不是"偏转大 = 慢"：**节奏恒定**。
> 本节其余三条（步长单位错误、A2 整路不响应、
> 夹取式落地）以及"两处方向必须一致"这个不变式仍然成立（两处现在都直接用同一个固定值）；
> 下文出现的 12.5 / 50 / 3.6 / 5.6 单位每秒等数值都按**当时**的公式算，已不代表当前固件。

**现场反馈**：五点示教状态下摇杆控制错乱 —— 推杆以后笔尖不是"一点一点挪"，而是
一推就窜、推得越狠窜得越快，斜着推还会把夹爪带开、把夹着的笔顶歪。

**先排除的三件事**（都不是原因，别再往这儿查）：
- **不是"两个控制器抢同一个关节"**：示教期间摇杆模块整段让位 ——
  `joystick_control.cpp:385` 的 `locked = pickPlaceIsBusy() | buttonControlLocked() | drawControlLocked()`，
  而 `drawControlLocked()` 在 TEACH 阶段为真，`if (!locked)` 把整个步进循环包住了。
- **不是轴向映射串了**：`teachJogTick()` 的 `amp[4]={st.base,st.shoulder,st.elbow,st.tool}` 与
  `raw[4]={st.sx,st.sy,st.ty,st.tx}` 和 `joyState` 的字段顺序（`joystick_control.h:85-94`）逐项对齐，
  A0→x、A1→y、A3→z、A2→f 没有错位。
- **不是反解/限位**：`moveToPoint()` 的 JOG 分支对超速部分夹取，不拒绝，不会卡死。

**真正的三个毛病**（都在 `draw_control.cpp` 的 `teachJogTick()` / `jogIntervalMs()` 里）：

1. **把"关节角度步长"当成了"工作区位移"**。旧代码
   `double step = speed.stepSize * DRAW_JOG_SCALE;` —— `speed.stepSize` 在手动模式里的含义是
   **每个控制周期转过的角度（度）**（`joystick_control.h:64`），默认 1.0；乘 0.5 之后
   在示教里却当**工作区单位**用，于是每格就是 0.5 单位（纸面半宽才 6，等于一格跳 1/12 个纸面）。
2. **步进间隔的方向写反了**。旧 `jogIntervalMs()`：`ms = slow - span*amp/512` ——
   满偏用**最短**间隔（10 ms），轻推用最长（40 ms）。这与同工程
   `joystick_control.cpp:272` 的 `speedIntervalMs()`（满偏用**最长**间隔，"慢而稳、最安全"）
   以及它自己的注释"偏转越大步越慢"**正好相反**。两条叠起来：轻推 0.5/0.04 = **12.5 单位/秒**，
   满偏 0.5/0.01 = **50 单位/秒** —— 而自动绘制才 `DRAW_V_MAX 3` 单位/秒。
3. **示教期间夹爪轴还活着**。A2 与 A3 是同一根右摇杆的两路，想压 Z 时手一歪就同时开合夹爪；
   夹爪里夹着笔（或笔夹），一动就把笔顶歪甚至掉笔，而"点动对点"根本不需要它。

**改法**：

| 项 | 旧 | 新 |
| --- | --- | --- |
| x/y/z 每格位移 | `speed.stepSize × 0.5` = 0.5 单位（还跟调速档位走） | `DRAW_JOG_STEP_MAX 0.25 × 偏转/512`，下限 `DRAW_JOG_STEP_MIN 0.02` 单位 |
| 步进间隔 | 满偏 10 ms、轻推 40 ms（推得越狠越快） | 轻推 `minDelayMs`、满偏 `fullDelayMs`（与手动模式同向；**v1.6.4 又把两者一起反转**为：轻推 `slowDelayMs`、满偏 `fastDelayMs`；**第二轮（m15921）再整段删除**，改成与偏转无关的固定 `speed.stepDelayMs` = 80/40/20 ms） |
| 满偏笔尖速度（默认档） | ≈50 单位/秒 | ≈6 单位/秒 |
| 轻推笔尖速度 | ≈12.5 单位/秒 | ≈1.6 单位/秒 |
| 末端 A2 | 跟手开合 | `DRAW_JOG_TOOL_ENABLE 0`：示教期整路不响应 |

- 满偏 0.25 单位/格 ÷ 40 ms ≈ 6 单位/秒，是自动绘制速度的两倍 —— 手动对点够灵敏，
  又不会"一推就飞"；轻推落到 0.02 单位/格（≈1.8 单位/秒）方便对准。
- 抓取/拒绝策略没动：仍是 `DRAW_JOG_MAX_DPS 200` + `moveToPoint(MOVE_XYZ_JOG)` 的夹取版，
  每格 0.25 单位远小于夹取上限，正常操作下不会触发夹取。
- 想要旧行为：把 `DRAW_JOG_TOOL_ENABLE` 改成 1；某一路方向反了就改 `DRAW_JOG_INVERT_X/Y/Z`。

**探针新增 7 条断言**（`probe_draw.cpp` 的 [6] 段开头，专治这四件事）：
单轴满偏只让对应坐标动（|串扰| < 0.02 单位）、每格位移 ≤0.26 单位、轻推步长小于满偏的一半、
A2 整路不响应（笔尖与 `angle4` 都不变）。**实测（probe_draw [6] 段，全部 PASS）**：

```

示教点动 A1：只让 y 增大（方向对、无串扰） PASS  dx=+0.000 dy=+0.182 dz=+0.000
```

满偏一格 0.182 单位、轻推 0.020 单位（旧版推到底 0.5 单位、轻推也是 0.5 单位），
串扰 `dy`/`dz` 实测 0.000 单位。探针在 [6] 段用的是 `setSpeed(0.5, 20, 60)`：
推到底（A0=900，对中心 512 的偏转是 388/512）间隔 `20+40×388/512 = 50 ms`
⇒ 笔尖约 **3.6 单位/秒**；出厂默认调速档（`stepSize 1.0 / 10 ms / 40 ms`）同一偏转
间隔 33 ms ⇒ 约 **5.6 单位/秒** —— 和自动绘制 `DRAW_V_MAX 3` 同一量级，
而旧版是 **12.5 ~ 50 单位/秒**（而且推得越狠越快）。真正推到底（A0=1023）时

**体积**：这次修复让默认配置从 `31706 B` 降到 **`31656 B`**（Uno 余量 550 → 600 B，

## 摇杆手感修正（v1.6.4，依据 p1.txt）

**现场反馈**（p1.txt，第三方分析）：没人碰摇杆时机械臂自己一小格一小格抽动；
轻轻碰一下飞快冲出去，用力推到底反而慢。

**先排除"串口冲突"**：串口用 D0/D1 的 UART，摇杆读 A0~A3 的 ADC，物理上完全隔离；
固件里 `serialProtocolLoop()` 是唯一的读串口者，`joystickLoop()` 只 `analogRead()`
（不发命令、不读串口）——两者不会互相打断。p1.txt 的结论也是同一个方向。

**真因（四条，前三条已改代码，第四条是硬件建议）**：

| # | 原因 | 改法 |
| --- | --- | --- |
| ① | 死区只有 15、标定只采 8 次且只做一次；ADC 噪声峰峰 ±5~±15、电位器温漂几十计数都会越过死区，一旦 `amp > 0` 就按最短间隔不停步进 | `JOY_DEADZONE 15 → 40`、`JOY_CAL_SAMPLES 8 → 32`、`JOY_CAL_MAX_OFF 64 → 80`；`readAxisAmp()` 新增**运行期中位跟踪**（偏差在门槛内时朝当前读数挪 1 个计数，第二轮又加了 `JOY_TRACK_MS 20` 时间门控） |
| ② | `speedIntervalMs()` 规律写反：偏转越小间隔越短 ⇒ 轻碰用最高速、满偏最慢 | **第二轮（m15921）已改为"没有这条规律"**：第一轮先反向成"偏转越大越快"并改名 `minDelayMs→fastDelayMs`/`fullDelayMs→slowDelayMs`，用户随即要求删掉该设置，于是把 `speedIntervalMs()` 与示教的 `jogIntervalMs()` **整段删除**，间隔改成与偏转无关的固定 `speed.stepDelayMs`（见下一节） |
| ③ | 关节步长与偏转无关（固定 `speed.stepSize`），死区边缘 1 个计数的抖动也走满一格 | 每格 = `speed.stepSize × 偏转/500`，下限 `JOY_STEP_MIN_DEG 0.1` 度（末端 `toolStep()` 本来就是比例缩放）——**这条保留**，第二轮删掉的只有"间隔随偏转变化" |
| ④ | 摇杆与舵机共用 5V，舵机一动 ADC 参考可能跌落；摇杆模块 X/Y 有串扰 | 硬件建议：摇杆单独供电、加 0.1µF 去耦；软件侧靠 ① 的死区与跟踪兜住 |

## 摇杆手感修正 第二轮（m15921）：删掉"推得越狠走得越快"+ 施密特迟滞

**用户要求**（m15921 原文节选）："删掉'推得越狠走得越快'的设置 / 修复大臂异常向前抖动的问题"。

1. **间隔不再随偏转变化**。`speedCfg` 从三个字段缩成两个：
   `struct speedCfg { double stepSize; int stepDelayMs; };`（默认 `{1.0, 40}`），
   `setSpeed(double stepSize, int stepDelayMs)` 两个参数**各自独立**校验（都只要 > 0），
   `adjustSpeed()` = `setSpeed(0.5 * (1 << level), 80 >> level)`：

   | 档位 | stepSize | stepDelayMs | 满偏线速度（约） |
   | --- | --- | --- | --- |
   | 慢 `SPEED_SLOW` | 0.5° | 80 ms | 6.25 °/s |
   | 中 `SPEED_NORMAL` | 1.0° | 40 ms | 25 °/s |
   | 快 `SPEED_FAST` | 2.0° | 20 ms | 100 °/s |

   于是"偏转"只决定**每格走多远**（③的比例缩放保留），**节奏恒定**——
   既不会轻碰就飞，也不会推到底反而变慢。

2. **施密特迟滞**（修"大臂自己一小格一小格往前抽"）。旧逻辑是
   `if (amp > 0) 步进`，而中位跟踪只在 `|d| < 40` 时介入 ⇒ 静态残余偏差落在
   **41~64 计数**这一段时既不被告踪吸收、又每 40ms 实打实走一格 0.1°，
   现场就是"没人碰摇杆、某个关节自己往前抽"。现在：静止时要跨过
   `JOY_DEADZONE + JOY_HYST 25 = 65` 个计数才起控（`s_axisHot[i]` 锁存），
   起控后门槛回落到 40（迟滞，防止在边缘来回抖）。中位跟踪同时加了
   `JOY_TRACK_MS 20` 时间门控——主循环是微秒级的，不加时间门的话
   几十个计数会在十几毫秒内被"追"成假中位。

3. **验证**：`probe_joystick` 新增迟滞回归（偏 +50 计数连续 200 轮四关节
   `Δ = 0.0000`）、`probe_draw` [6] 段与 `probe_move` 档位段跟着改成固定间隔。
   **两个探针一开始 FAIL，但都是 fixture 写错、不是固件 bug**，教训值得记：
   - 迟滞是**锁存状态**：上一段把某路推过 65 后门槛已降到 40，此时再给 +50
     就被合法当成推杆；必须先 `resetInputs() + posInit() + joystickSetup() + runLoop(2,20)`
     把回中、重新标定（`s_centerOff` 归零）与 `s_axisHot` 清干净再测。
     实测当时 `Δb=+10 / Δr=Δc=−10` 恰好等于 100 格 × `JOY_STEP_MIN_DEG 0.1`。
   - `setSpeed()` 从 3 参数变 2 参数后**没有交叉校验**了：`setSpeed(1.0, 0)`
     会合法地"只改步长、保留原间隔"，不能再断言"整组配置不变"。

**可回退**：想恢复"间隔随偏转插值"，把 `speed.stepDelayMs` 的用法换回
一个插值函数即可（`speedCfg` 加回字段、`joystickLoop()` 与 `teachJogTick()`
两处必须同向）；迟滞只需把 `JOY_HYST` 置 0。

**上机排查手段**：把 `joystick_control.cpp` 的 `WEARM_JOY_DEBUG` 改 1，固件会
"有动作时 + 每 500ms"打印 `raw A0..A3`、四路偏转量 `amp`、四个关节角与 `rec`
（用例：手完全松开，看哪一路 raw 偏离 512 最多 / 有没有串扰；`Serial.print` 浮点
会链进约 1.5~2KB 格式化层，三功能全开的 Uno 只剩几百字节，需同时
`-DWEARM_ENABLE_DRAW=0` 才装得进）。

**探针**：`probe_joystick` 新增 [10] 段（同起点同时间"大幅偏转位移 > 小幅"、
每轮漂移 +1 共 +110 计数被跟踪吸收）与**迟滞回归**（偏 +50 计数连续 200 轮四关节
一动不动）；`probe_move` 的档位段（固定间隔下"每格步长"仍按档位不同）、
`probe_joystick` 的 [5]/[9] 段、`probe_draw` 的 [6] 段都跟着新死区、固定间隔
与新字段名改过 —— 这些断言在**旧代码上会失败**，也就是说它们是这次修正的回归测试。


## 本轮改动 —— 删除夹爪"高度/角度范围限制"、夹物与绘图每帧夹紧（多文件版）

**需求**（用户原话）：删除夹爪高度范围限制；夹物和绘图时**每一帧**都要把夹爪夹紧。
本轮先改多文件版；发版（v1.6.5）时已重跑 `.selfcheck/make_single.ps1` 把单文件
同步再生成（301756 B / 6713 行，SHA256 `BBE60B06…`），`run_all.ps1` 全绿。

### 1) 删掉的三处"范围限制"

| 位置 | 原来的行为 | 现在 |
| --- | --- | --- |
| `constant_and_positions.cpp` `getAngleEx()` 的 f 越限处理 | `minF=60 / maxF=150`；越限时按 `servoLimitMode` 走 `SERVO_LIMIT_REJECT`（反解失败）或 `SERVO_LIMIT_CLAMP`（把 `angle4` 吸附到 60/150 并置 `*clamped=true`） | 整块删除。反解只决定 b/r/c，`angle4` 原样保留，`*clamped` **恒为 false**（形参保留，`path_core` 的调用点不用改） |
| `constant_and_positions.cpp` `posSetAngle4()` | `clampDouble(angleDeg, 60.0, 150.0)` | `clampDouble(angleDeg, TOOL_ANGLE_MIN, TOOL_ANGLE_MAX)` = **0~180** |
| `draw_control.cpp` `drawSetPaperZ()` | 要求 `z ∈ [DRAW_PEN_Z_MIN, DRAW_PEN_Z_MAX]`（-5~30） | 只拒绝 NaN，**任意有限值都接受**（两个宏已删） |

`constant_and_positions.h` 里旧的 `struct servoLimitCfg` 早就删了，这次把残留的
`SERVO_LIMIT_CLAMP` / `SERVO_LIMIT_REJECT` 与 `extern int servoLimitMode` 一起删掉，
换成末端夹爪自己的常量（名字统一成 `TOOL_*`，串口 `O`/`S` 与取放都引用它们）：

    TOOL_ANGLE_MIN   0.0     /* 舵机电气行程下限 */
    TOOL_ANGLE_MAX   180.0   /* 舵机电气行程上限 */
    TOOL_ANGLE_OPEN  150.0   /* 名义"张开"角（与串口 'O' 一致） */
    TOOL_ANGLE_CLOSE 60.0    /* 名义"合拢"角（与串口 'S' 一致） */
    TOOL_ANGLE_TIGHT 55.0    /* 真正"夹紧"角：比名义合拢再压 5° */
    TOOL_MIRROR_SUM  210.0   /* 夹爪装配镜像和 physical = 210 - logical */

**为什么还留 0~180**：这是舵机的电气行程（脉宽 544~2400us），不是"夹爪范围限制"。
完全放开就会出现 `angle4 = -37` 这种无意义值 —— 摇杆、串口、录制回放都能写进来，
硬件上根本走不到那个角度。**为什么夹紧角是 55 而不是 60**：60 是"名义合拢"，
夹爪在 60 只是碰到物体、没有夹持力；再压 5° 才有夹紧力矩。9g 舵机不能压太多
（堵转会把 5V 轨拉崩），实测夹不住就把 `TOOL_ANGLE_TIGHT` 调小（例如 50），
松不掉就调大。

### 2) "每一帧都夹紧"是这样实现的

不新增状态、不新增定时器：**每帧重申一次目标角**，靠"值没变时 `posSetAngle4()`
返回 false 且不写状态"来保证无副作用（舵机本来就是每帧刷新脉宽）。

- `pick_place.cpp` 新增：

      static bool pickHoldingStage(int st) {
        return st == PICK_ST_DWELL_CLOSE || st == PICK_ST_LIFT ||
               st == PICK_ST_TRAVERSE    || st == PICK_ST_DESCEND_DST;
      }

  在 `pickPlaceLoop()` 的 kind 分派之后、`if (stageDone) advanceStage();` 之前：

      if (s_kind != PICK_KIND_TOOL && pickHoldingStage(s_stage)) {
        (void) posSetAngle4(PICK_TOOL_CLOSE_ANGLE);   /* = TOOL_ANGLE_TIGHT */
      }

  即"合爪之后、松爪之前的每一帧"。`PICK_TOOL_CLOSE_ANGLE` 现在就是
  `TOOL_ANGLE_TIGHT`（原来等于 60），`PICK_TOOL_OPEN_ANGLE` 就是 `TOOL_ANGLE_OPEN`（150）。
- `draw_control.cpp`：`drawLoop()` 在 `if (s_paused) return;` 之后、`switch (s_phase)`

## 本轮改动 —— 恢复末端笛卡尔范围配置 `rangeLimit`（z −60~60）

**需求**（用户原话）：把机械臂顶端笛卡尔坐标系的 **z 坐标范围调到 -60~60**。
当前代码里已经**没有任何**末端范围配置（v1.6.5 那轮"去配置化"把 `struct rangeLimit`
连同 `clampToRange()` / `rangeClampConfig()` 一起删了），所以本轮按用户的选择
**恢复 v1.6.4 的 `struct rangeLimit limit`** 结构体：x/y 保持 ±40、z 改成 **−60~60**，
并把越界判据重新接回原来那两个位置。

### 1) 恢复的东西

| 位置 | 内容 |
| --- | --- |
| `constant_and_positions.h` | `struct rangeLimit { double minX, maxX; double minY, maxY; double minZ, maxZ; };` + `extern struct rangeLimit limit;` + `int rangeLimitConfig(void);`，声明紧跟 `extern struct arm arm1;` |
| `constant_and_positions.cpp` | `struct rangeLimit limit = { .minX = -40.0, .maxX = 40.0, .minY = -40.0, .maxY = 40.0, .minZ = -60.0, .maxZ = 60.0 };`（放在 `struct speedCfg speed` 之前）；`rangeLimitConfig()`：某个轴 `min > max` 就地交换并返回被改的轴数，`posInit()` 第一行调用（幂等） |
| `path_core.h` `pathCorePointOk()` | 开头三次纯比较 `if (x < limit.minX || x > limit.maxX) return false;`（y / z 同）—— 取放与绘图在**采样阶段**就把越界轨迹整条否掉 |
| `move.cpp` `posOutOfRange()` | 关节步进算完 `nextRec` 后，三轴任一越出盒子就 `return MOVE_AT_LIMIT`（**整步回退**，不是把坐标夹到边界上）；挂在 `moveJointStep()` 的第 4 步 |

`clampToRange()` / `rangeClampConfig()` 这两个旧辅助函数**没有恢复**：它们只服务于
"把 `Pos.rec` 拉回盒子"这一种用法（`posInit()` / 回中），而本版 `POS_HOME` 与全部取放、
绘图点都在盒内，拉回的代码只会变成死代码。**另外别用 `clampToRange()` 复刻越界判据** ——
v1.6.4 实测过：`move.cpp` 自身能省约 94 B，但 LTO 让 `draw_control.cpp` 涨 212 B，净亏 82 B。

### 2) 为什么"z 改成 ±60"在行为上什么都不会变（**重要**）

几何决定的真实末端范围是 **z ∈ [−20, 40]**（L1 = L2 = 20、`armheight = 0`、关节都在 0~180°：
z = 20·sin α + 20·sin β，最低 −20 在 (r,c) = (0,90)，最高 +40 在 (90,0)），
而且它随水平半径收窄 —— ρ = 20 时只剩 **z ∈ [−20, 20]**。
所以盒子取 z ±60 **比真实包络还宽 40（下）/ 20（上）**，x/y 又正好等于包络端值
（`probe_axes` 打印的 6 条余量：x[0.00,0.00] y[0.00,0.00] z[40.00,20.00]）
⇒ **它拦不住任何可达姿态**，改完的行为与改之前完全一样。

真正让 z 停在 ±19 附近的不是这个配置，而是**几何 + 关节硬限位 0~180 +
`getAngleEx()` 的残差上限 0.05**。另外"超出 ±19 回 `BUSY`"也不可能来自坐标指令：
串口 `x/y/z` 是**三个关节角**、越界只按 0~180 夹取、从不回 `BUSY`（`serial_protocol.cpp:627-648`）；
回 `BUSY` 的只有取放 `A`/`B`/`C`（`:574`，`pickPlaceStart()` 返回 −1 / −3 或忙 −2）
与绘图 `D/G/E/Q/U/W`（`:603`）。
**要让末端真的走到 z = ±60，必须先加长两臂**（`constant_and_positions.cpp` 里的
`struct arm arm1`）：改成 80/80 后包络变成 z ∈ [−80, 160]、x/y ±160，那时盒子也要一起放宽，
否则它反而会成为有效边界。

### 3) 连带改动的注释与探针

## 本轮改动 —— 修正肩/肘角度映射（v1.6.6：α = 90° − r、β = c − 180°）

### 1) 症状：真机姿态与模型对不上，z = −25 的取放一路 BUSY

- 台面按 100 mm 深摆（`PICK_GRASP_Z -25.0`，本固件的 1 单位 = 4 mm），三个物体一按 `N`
  就回 `BUSY`；`pickPlaceStart()` 返回 **−3**（路径校验失败），
  串口把它翻成 `BUSY`（`serial_protocol.cpp:574`）。
- 真机上贴整行命令 `x=90,y=0,z=90`（串口 `x/y/z` 写的是**三个舵机角**：
  `x -> angle1(b) 基座`、`y -> angle2(r) 上臂`、`z -> angle3(c) 下臂`，
  见 `serial_protocol.cpp:628-629`、`:768-769`）后观察到：
  **上臂竖直朝上、下臂竖直朝下**。
- 而 v1.6.5 的 `recFromServo()` 是 `α = r`、`β = r − c`，同一条命令正解出来是
  "上臂**水平朝前**、下臂竖直朝下" —— 与实测矛盾。这就是根因所在。
- 另一条独立证据：官方 [MeArm-Arduino](https://github.com/MeArm/MeArm-Arduino)
  的 `ik.cpp` 里 `a1`（肩）是**上臂相对水平的绝对角**、`a2`（肘）是**小臂的绝对角**
  （`a2 = C + a1 − PI`），`MeArm.h` 的默认标定也把两个舵机都当"地面参考"的绝对角
  （外推肩舵机 0 号位 ≈ 上臂朝上偏后，与本固件的 `r = 0` 同向）。

### 2) 新映射与为什么

```
α = 90° − r      r = 0° 竖直朝上、90° 水平朝前、180° 竖直朝下
β = c − 180°     c = 0° 水平朝后、90° 竖直朝下、180° 水平朝前
```

- 两者都是**地面参考的绝对角**，两杆的几何夹角 `α − β` 仍由 `c` 唯一决定，
  与"肘是上臂上的铰链"这一机械事实不冲突（旧式子的 `tr[i].r − tr[i].c` 也是同构的）。
- 旧式子的可达包络 z ∈ [−20, +40]（`z` 下限只有 `−L2`），新映射是 z ∈ [−40, +20]：
  这才是"两节各 20 单位、往下能压到 −40"的真实包络，也正好让 100 mm 深的台面
  （z = −25）落进来。

### 3) 改了什么

- `constant_and_positions.cpp` 的 `recFromServo()`：`α = (90 − r)`、`β = (c − 180)`
  （原来 `α = r`、`β = r − c`）。
- 同文件 `getAngleEx()`：解出平面几何角后换算回舵机角
  `r = 90 − α`、`c = β + 180`（原来直接 `r = β + δ`、`c = δ`）；
  `ikBranch()` 的注释改成"δ 是两杆几何夹角，不是舵机角"。
- `POS_HOME`：`(20, 0, 20)` → **`(20, 0, -20)`**。理由：真机初始位姿是
  `(b,r,c) = (90,90,90)`，在新映射下正解就是 `ρ = L1 = 20`、`z = −L2 = −20`；
  若保留 `(20,0,20)`，同一反解会变成 `(r,c) = (0,180)`（两个轴都压死在行程端点）。
  这样**物理上的开机姿态与以前一模一样**，只是模型对它的坐标描述变了。
- `meArm.ino`、`joystick_control.h`、`constant_and_positions.h` 的"坐标模型/包络"注释
  同步（新的 z 包络、新的初始位姿坐标）。
- 根 `README.md` 的"运动学"整节重写（映射表、正解、反解、分支族、待机位）。

### 4) 中途踩的坑：镜像分支残差打平 → 段内跳 60~80°

第一次改完跑 `run_all.ps1` 是**红的**：`probe_pick_place` 全部 `rc=-3`、
`probe_draw` 47 项失败（`validatePath()` 直接不过）、`probe_button`/`probe_pins_off` 连锁失败。

用 `.selfcheck/out/diag_path.cpp`（临时诊断，`out/` 不入库）复刻采样后定位到：
两杆平面机构对同一个点本来就有两个镜像解（`δ = ±acos`），**在新映射下这两个解都能落进
r/c 的 0~180° 行程、残差又都是 0**，于是 `getAngleEx()` 的"取 err 最小"靠浮点尾数随机挑
⇒ 同一条直线上相邻采样点来回换分支，关节角一次跳 60~80°（实测第 49/61 点
`r: 91.18 → 155.41`、`c: 114.54 → 177.39`），"段内不许换分支"（25° 门限）必然失败。
旧固件里 `c` 就是 δ、且受 c ∈ [0,180] 限制，**等效于只允许 δ = +acos 这一族**，
所以历史上从没暴露过这个问题。

修法（分了三次落地，前两次都不够）：
1. 先把候选收成"正/反平面 2 个、δ 固定取 `+cAbs`" —— 分支策略与修复前逐位一致，
   跳变立刻消失（`diag_path` 里 10 段全部 `OK（全段可用、无跳变）`，`cand0` 在每一段的
   每个采样点都可用），`probe_pick_place`/`probe_button`/`probe_pins_off` 随之转绿。
2. 但"只留 `+cAbs`"会**漏解**：`probe_rt` 的往返扫描出现 **273/2028 组反解 false**，
   失败样例全是 `r = 0`（手臂朝反平面）的点 —— 这些点只有 `−acos` 那一族能落进行程。
   最终策略 = **4 个候选（正/反平面 × δ = ±acos）按优先级挑选**：先试 `+acos` 两族
   （与修复前同一族 ⇒ 段内不跳），整族都不合格才退到 `−acos`；候选还必须通过
   `err ≤ 0.05`（否则会出现"在行程内但解是错的"）。
3. 另外发现 `c` 会算出 **360°**：本模型下 `α − β = 270° − r − c`，取值跨到
   `[−90°, 270°]`，于是端点 `(20,0,20)`／`(−20,0,20)` 这类"臂折到极限"的点会被
   atan2/asin 分支算成 `c = 360°`（与 `c = 0°` 是同一物理位姿）而被 0~180 判据否掉。
   修法：`rDeg`/`cDeg` 先过 `normRevAngle()`（把贴 360° 的值折回 0°、负值折进
   `[0°, 360°)`）再做行程判据，b/r/c 三轴共用；旧模型 `α − β = c ∈ [0°,180°]`
   从不越界，所以这个坑历史上不存在。

### 6) 映射之外又逮到两个真 bug（都是这一轮才暴露的）

新映射一上线，`probe_axes` 立刻全绿，但 `probe_rt` 的第 3 个端点用例和 `probe_draw`
的全部内置图形转红。两个都**不是映射本身写错**，而是老代码里被旧模型"掩盖"着的缺陷：

**(A) `r = 180` 端点被 `RADtoDEG` 截断的 π 误杀**
- 症状：`(0,0,−40)`（期望 `r=180, c=90`）`getAngle()` 回 false，固件日志
  `[kin] reject: no planar branch fits the joint travel` ⇒ 四个候选全被 `continue`。
- 定位：`constant_and_positions.cpp` 里加 `#ifdef WEARM_IK_TRACE`（只在 PC 自检里用
  `-DWEARM_IK_TRACE=1` 编译，AVR 侧不定义、不参与编译），打印每个候选：
  `cand 0 b=90.000000 rhoP=0.000000000 delta=0.000000000000 betaDeg=-90.000000
  rDeg=180.000000 cDeg=90.000000 err=0.000000000000` + `reject: r out of travel`。
  打印只有 6 位小数，看不见真正的越界量。
- 原因：`constant_and_positions.h` 的 `#define RADtoDEG (180 / 3.1415926535)`——
  π 只写了 10 位有效数字，相对误差 3.5e-11，换到 90° 就是 **3.2e-9°** 的绝对误差，
  比 `getAngleEx()` 里 `const double EPS = 1e-9` 的行程容差还大 ⇒ `rDeg` 实测
  180 + 3.2e-9，`!(rDeg <= 180 + EPS)` 命中。旧映射里 `c = delta`、角度由同一套
  公式往返，永远走不到 180 这个端点，所以这个偏差从来没被踩到。
- 修复：`RADtoDEG` 改用完整 π（`180.0 / 3.14159265358979323846`）；`getAngleEx()`
  的 `EPS` 由 `1e-9` 改成 `ANGLE_EPS`（`1e-6`，与"−0.0 归零"同一口径）。
- 验证：`probe_rt` §1.5 三条端点用例（`(20,0,20)→r=0,c=180`、`(−20,0,20)→r=0,c=0`、
  `(0,0,−40)→r=180,c=90`）全部 PASS。

**(B) 绘图默认纸面高度物理上不可能：`−12.0` → `−28.0`**
- 症状：6 个内置图形全部 `[draw] 轨迹校验失败，拒绝开始绘制`。
- 定位：`draw_control.cpp` 的 `validatePath()` 加 `#ifdef WEARM_DRAW_TRACE`
  → `vp1 hp=20.000,0.000,-20.000 ap=14.000,0.000,12.000 pts=2` +
  `vp1: home->lift segment rejected`：抬笔点在 z=+12（老模型的纸面高度），
  从待机 −20 一步跨到 +12 必然超过 `DRAW_BRANCH_JUMP_DEG 25°` 的分支门限。
- 原因：新映射下待机末端是 `(20,0,−20)`，铅笔是**刚性**固定在夹具上的，
  纸面只有落在待机**下方**才可能被笔尖碰到。`−12.0` 是"把老模型的 +12 直接取负号"
  得到的，物理含义变成"纸面比待机高 8 单位"——笔尖永远碰不到纸；顺带还让
  "抬笔平移全程高于纸面"这条自检必然失败（平移起点就是待机 z = −20）。

## 本轮改动 —— 按 RC-robot-hand 修正肘轴映射（β = c − 90°）+ 待机位/纸面/包络

上一轮（v1.6.6）只把肩轴修对了（`α = 90° − r`），肘轴写成了 `β = c − 180°`。
按用户提供的参考工程 `others/RC-robot-hand`（同型号机械臂）的实测任务表复核后，
肘轴应当是 `β = c − 90°`。

### 1) 症状：取放的上下方向整体反了

- 复现：走一遍自动取放，夹爪朝目标下降时真机反而抬高，随后一路 BUSY。
- 根因：`β = c − 180°` 把"末端下降"反解成了"末端上升"。真机上肘舵机角度越大
  末端越高（c 与 β 同号），`c − 180` 让这个关系整体翻转，且映射后可达包络的
  z 方向也跟着镜像。

### 2) 依据：RC-robot-hand 的实测任务表

`others/RC-robot-hand` 与本题机械臂同型号，它把"提臂"和"收臂"分开记录：

| 动作 | 变化的舵机 | 末端 |
| --- | --- | --- |
| 提起 | 只改 F（D7，对应本题 c） | 升 |
| 收回 | 只改 R（D8，对应本题 r） | 升 |

即 F↑ ⇒ 末端升。把 F 记作 c，就要求 `β = c − 90°`（c=0 竖直朝下、
c=90 水平朝前、c=180 竖直朝上），而不是 `c − 180°`。

### 3) 改了什么

- `constant_and_positions.cpp:144-145` FK：`alpha = (90.0 − r)/RADtoDEG`、
  `beta = (c − 90.0)/RADtoDEG`（`α = 90° − r` 与 `θ = 90° − b` 不变）。
- `constant_and_positions.cpp:285-286` IK：`rDeg = 90.0 − alphaDeg`、
  `cDeg = betaDeg + 90.0`；`ikBranch()` 仍是纯几何（`delta = alpha − beta`，未动）。
- `POS_HOME`：`{40,0,0}` → **`{20,0,-10}`**。旧值落在可达边界（ρ = L1+L2 = 40）
  上，点动 A0/A1（x+/y+）永远被 `isReachable()` 拒掉、示教也走不动；新值是
  折叠在内部的姿态（IK 解 b=90、r=60.55、c=7.43），x+/y+/z− 都能动。
  **【后记 · 已按用户要求改回 `{40,0,0}`，见文末"初始位姿改回 (40,0,0)"一节】** ——
  用户指出真机上电姿态必须是舵机 `x90,y90,z90`，而折叠位在物理上是 90/60.55/7.42，
  不等价；代价（无法再向外伸、就地垂直抬升无解）由取放模块的 `s_riseAtSrc` 兜住。
- 绘图默认 `draw_control.cpp`：`DRAW_PEN_Z_DEFAULT` −28.0 → **−20.0**；
  `DRAW_CENTER_X_DEFAULT` → **27.0**。
- 包络：`x[0,40] y[-40,40] z[-40,40]`；`rangeLimit` 三轴都放开到 ±40
  （不再只放 z）。

### 4) 纸面与中心 x 为什么跟着变

待机从 (20,0,−20) 挪到 (20,0,−10) 后，纸面必须仍在待机下方（铅笔刚性固定在
夹具上、笔尖朝下）。取 **−20.0**：在待机下方 10 单位（1 单位 = 4 mm ⇒ 露出约
40 mm），且 z=−20 平面上可达 ρ∈[20,34.6]，足够放下 12 单位宽的绘制带。
中心 x 取 **27.0**，让 x∈[21,33] 落在可达带正中。上一轮按旧待机推出的
−28.0 随之作废。

## 本轮改动 —— 取放模块全量重写（8 步路径 / 物体高度 ±10cm）+ 绘图轴向修正 + 分支拆分

### 1) 取放：从"两点直线插补"改成指定的 15 段路径

`pick_place.cpp` 整个重写。阶段枚举（也是 `pickPlaceStageName()` 给探针看的字符串）：

`idle → rise-src → to-behind → descend-src → reach-in → close-tool → squeeze-tool →
dwell-close → lift-src → traverse → descend-dst → open-tool → dwell-open → retreat →
go-home → idle`

对应"抬到物体高度+5cm → 沿水平退到物体后方 2cm → 降到物体同高 → 向前 2cm 进爪 →
合爪夹紧 → 停顿 → 抬回飞行高度 → 平移到目标正上方 → 下降 5cm → 张爪 → 停顿 →
抬回 → 回初始位姿"。

几个关键实现（**不是随手写的常量，都有依据**）：

- **"物体后方 2cm"是沿基座径向退让**，不是固定 −x：`pickBehindPoint()` 用
  `k = PICK_BACK_DZ / sqrt(x²+y²)` 算 `out = p − p·k`。夹爪的钳口本来就沿基座径向
  伸出，物体 |y| 大时固定减 x 会偏出几十度。
- **飞行高度自适应**：`planTravelZ()` 从 `max(src.z, dst.z) + PICK_LIFT_DZ(5cm)`
  以 1 单位步长往下试，直到 `top + PICK_CLEAR_DZ(1cm)`，逐个用 `pathCorePointOk()`
  验 7 个点。原因是**可达域本身是个环带**：高度 z 处可用水平半径
  `ρ ∈ [20·√(1−(|z|/20−1)²), √(1600−z²)]`（z=±25 时是 [19.36, 31.23]），
  物体越高、理想飞行高度越出域，所以只能压低飞行高度（A/B/C 实测 −7.50 / 12.50 / 29.50）。
- **物高门限 ±25 单位（=±10cm）**，超出直接返回 −4；当前位姿不在自己那条 IK 分支上
  或起步点不可用返回 −3；7 段路径采样校验（`pathCoreSegmentOk()`）不过也返回 −3。
- **搬运全程每帧重压夹紧角**：`pickHoldingStage()` 覆盖 dwell-close / lift-src /
  traverse / descend-dst，每帧 `posSetAngle4(PICK_TOOL_SQUEEZE_ANGLE)`；这修的是
  "夹起来的过程中夹爪慢慢松开"。合爪阶段分两步：先 `TOOL_ANGLE_CLOSE` 快合，
  再用 12°/s 的慢速压到 `TOOL_ANGLE_TIGHT`（45°）。
- **回初始位姿是关节空间插值**（`PICK_KIND_HOME`，复用 s_fromX/Y/Z/s_toX/Y/Z
  当角度暂存），不是再走一次反解 —— 避免最后一段又碰到分支跳变。
- 新增导出 `pickPlacePlanZ(int, double*)`（只规划不改状态）与 `pickPlaceBackDz()`，
  探针靠它们验"计划高度落在 [最高点+1cm, +5cm]"和"后方点"位置。

## PowerShell / 脚本的几个坑

1. **`& $gpp ... 2>&1` 赋给变量后 `$LASTEXITCODE` 仍是 0** —— g++ 的 warning 走
   stderr，只看退出码会漏掉警告（历史上就这样漏过两个 `-Wunused-*`）。
   判定失败要**同时看"输出行数 > 0"**。`run_all.ps1` 已经这么做了。
2. **`.ps1` 必须存成 UTF-8 带 BOM**。Windows PowerShell 5.1 读无 BOM 的 `.ps1`
   会按 ANSI(GBK) 解码：中文注释变乱码只是表面现象，真正的坑是**一个汉字吃掉
   后面的一个 ASCII 字节**——于是某个字符串的收尾引号被吞掉，报错却指在完全
   无关的行上（实测报 `run_all.ps1:46` 的 `"$_" }` 是"意外的标记"，而问题
   在第 36 行的中文行；还会把两行粘成一行，报的行号根本对不上）。
   本仓库的 `.ps1` 都带 BOM，**改完一定要确认 BOM 还在**（很多工具覆盖写入
   会丢掉它）。`.selfcheck\ensure_bom.ps1` 就是干这个的：
   `& .\.selfcheck\ensure_bom.ps1` 补齐 BOM，`-Check` 只检查不改。
3. **本机是 Windows PowerShell 5.1，没有 `pwsh` 7**。脚本里别用 7 才有的语法，
   命令行也不要写 `pwsh -Command ...`（会报"无法将 pwsh 项识别为..."）。
4. **执行策略**：直接 `& .\.selfcheck\avr_build.ps1` 可能报
   `AuthorizationManager 检查失败...UnauthorizedAccess`。
   在每个新 shell 里先跑
   `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force`。
5. **想看固件自己的日志不用重编**：mock 的 `Serial` 默认把输出吃掉，
   设环境变量 `WEARM_MOCK_SERIAL=1` 后 `MockSerial::print()` 会直接 fputs 到 stdout
   （见 `.selfcheck/mock/Arduino.h` 的 `mockSerialOn()`）。于是可以拿**现成的探针 exe**
   复跑一遍看固件为什么拒绝，例如：

   ```powershell
   $env:WEARM_MOCK_SERIAL='1'; & .selfcheck\out\probe_draw.exe > $env:TEMP\pd.log 2>&1
   ```

   （`$env:WEARM_MOCK_SERIAL='1'` 写出的日志是 UTF-16LE，`read` 工具会当二进制；
   用 `Get-Content` 或 `[System.IO.File]::ReadAllText($p,[System.Text.Encoding]::Unicode)` 读。
   `run_all.ps1` 自己写的 `out\<探针>.log` 是 UTF-8，可以直接读。）
6. **要做条件编译的调试打印**：`#ifdef WEARM_IK_TRACE` / `#ifdef WEARM_DRAW_TRACE`
   （默认不定义 ⇒ AVR 与常规 PC 编译都不受影响），只在本地重编那一个 TU 时加
   `-DWEARM_IK_TRACE=1`，然后重新链接探针。本机单个固件 TU 要 4~5 分钟，
   所以把对象文件留在 `out/obj/`（带 trace 的版本放 `out/obj/tr/`），
   之后只做链接（几十秒）。

## 已知的"上机才能确认"项

代码层面无法验证、需要接上真机试的：

1. **哪根摇杆轴接在 A0/A1 与 A2/A3**：若左右手反了，把
   `joystick_control.cpp` 里 `JOY_L*` / `JOY_R*` 两组引脚对调。
2. **末端开合方向**：现按旧手柄版约定「A2 **右推 = 收回**、左推 = 张开」
   （`joystick_control.cpp` 里 `(raw > JOY_CENTER) ? -1 : 1`）。
   若手感相反，把那个三元式对调即可。
3. **`c` 接近 180° 的机械干涉**：下臂 c 的行程已放开到 180（舵机电气行程上限，理论值），
   但下臂在接近 180° 时会往后折回，代码注释已警告这是"理论行程上限、
   不保证不撞"。**请先在慢速档、空载、抬离台面的情况下单步试。**
4. **`limit` 是软护栏，而且比真实包络宽**：基座可摆到 x<0 后方、末端最低到 z≈-20.0。
   盒子取 x/y ±40、z −60~60：x/y 与包络端值重合（余量 0），z 比包络宽 40（下）/20（上），
   所以它**拦不住任何可达姿态** —— 只有把配置收窄（或加长两臂 `arm1`）它才会成为有效边界。
   同样建议先慢速空载试。

5. **`r` 走到 0° / 180° 的机械干涉**：上臂 r 的行程已放开到 0~180（舵机电气行程）
   （r=0 上臂水平朝前、r=180 上臂水平朝后）。与 c 组合后末端最低可到肩关节
   以下约 20，可能撞台面或底座。**请先在慢速档、空载、抬离台面的情况下
   单步试**，确认行程两端不会撞到东西再放开跑。

6. **A/B/C 三个物体的实际摆放位置**：`pick_place.cpp` 顶部的 `PICK_SRC` 与
   `PICK_DST`（当前设计值：取 A(24,16,−20) / B(24,−12,0) / C(26,0,20)，
   放 A(15,−18,−20) / B(18,16,0) / C(20,−16,20)）只是"设计值"，真机上是把物体摆在
   哪儿就改哪一行（单位与坐标模型一致，`x/y` 是水平面、`z` 是高度，1 单位 = 4 mm）。
   第一次跑取放序列请务必：先进慢速档（串口发 `L` 或 `1`），**卸掉夹爪里的物体**，
   用 `A` 试跑一遍，观察三件事：
   (a) **"物体后方 2cm"是不是真的落在物体后面** —— `PICK_BACK_DZ` 是沿基座**径向**
   退让（不是固定减 x），物体 |y| 大时看起来会斜着退，这是有意的；
   (b) **抬升高度是否真的抬高** —— `PICK_LIFT_DZ`（5cm）是理想值，可达域装不下时
   `planTravelZ()` 会自动压低，实际规划值可以用探针的 `pickPlacePlanZ()` 看；
   (c) **抬起与平移途中夹爪是否一直夹紧** —— 本轮起每个搬运帧都会重压夹紧角。
   物高超过 ±25 单位（±10cm）时 `A`/`B`/`C` 返回 `-4` 拒绝启动，不会乱走。
   序列速度 = 当前档位（慢 25 / 中 50 / 快 90 度每秒），夹爪合紧段 60 度每秒、
   压紧段 12 度每秒。

7. **物理按键默认不接、也默认不读**（本轮变更）：固件从本轮起默认
   `WEARM_BUTTON_PINS = 0`（`weArm_config.h` 第 4 节），**完全不读 D2~D5**
   （连 `pinMode` 都不做），四个按键的功能全部改由串口字符触发：
   `N` 循环执行 / `R` 录制开关 / `P` 播放 / `M`（或 `0`）回中。
   起因：本机 D2~D5 上没有独立按键，只把摇杆自带的 SW 脚接到了 D2（= 按键1
   循环取放），而**右摇杆推到最前时机械上会压合那颗轻触开关**，于是手动推杆
   推到极限就假触发一次取放、摇杆随即被 `locked` 锁住（现象：右摇杆向前本该
   转下臂，结果触发了自动取放）。要恢复物理按键接线：把 `WEARM_BUTTON_PINS`
   改成 1 即可（D2~D5、一端接按键、另一端接 GND、按下为低电平；固件用
   `INPUT_PULLUP`，接反或悬空会一直读到"按下"）。改回 1 后上机逐个试：
   按一下 D2 是否开始夹 A、再按是否换 B；D3 是否进入「录制中」、再按是否
   报保存成功或"太短/没有位移"；D4 是否复现；D5 是否回到 `POS_HOME` 姿态。
   注意**回放按录制时的时间轴走**，与当前调速档位无关，所以第一次录制建议
   用慢速档录一小段、观察回放是否与手动操作一致。
   （PC 探针 `probe_button` / `probe_draw` 靠模拟 D2~D5 电平测按键逻辑，
   `run_all.ps1` 给**探针**额外加了 `-DWEARM_BUTTON_PINS=1`，固件 TU 仍按默认
   0 编译，两条路径都会被严格编译一遍。）

8. **纸面高度 `z` 与铅笔的固定**：`draw_control.cpp` 的 `DRAW_PEN_Z_DEFAULT **-20.0**`
   （= 初始位姿末端 `(40,0,0)` 再往下 20 单位）
   只是按几何推出来的**出厂估计值**。上机第一步仍是**标定**：用手动方式把笔尖
   移到纸面、读串口角度或用 `x/y/z` 指令把笔尖压到纸上，然后用
   `p<数值>` 把这个高度告诉固件（`drawGetPaperZ()` 会打印）。**`p` 现在不接受的范围
   只有一个：NaN**（标定范围 -5~30 已在"删除夹爪范围限制"那一轮删掉）。
   铅笔要夹紧、
   笔尖比夹爪低出来的长度一旦变了就要重标，否则要么画不上、要么把纸戳破。
   抬笔高度 `DRAW_LIFT_DZ 4.0` 若发现抬起来还是蹭到纸，把它调大。
   （注意标定值必须是**负**的、且比初始位姿的 `z=0` 更负：纸面高于初始位姿末端时笔尖够不到，
   而且"抬笔平移"会从初始位姿直接穿到纸面以下。）
9. **五点示教时 A0/A1/A3 的轴向与手感**：示教点动用的是笛卡尔点动
   （A0→x、A1→y、**A3 前推→z 下降**）。若发现推杆方向与预期相反，
   改 `draw_control.cpp` 顶部的 `DRAW_JOG_INVERT_X/Y/Z`（0/1 翻转），
   **不要动摇杆模块本身** —— 那里的方向约定是给手动关节控制用的。
   手感按"每格 ≤0.25 单位、轻推 0.02 单位"调：嫌太慢就加大 `DRAW_JOG_STEP_MAX`
   （但它同时是"一格最多跳多远"的上限，别再加回 0.5），嫌太快就调小或把
   `DRAW_JOG_STEP_MIN` 调小。**示教时不响应 A2（夹爪）**：要让右摇杆左右推也能开合夹爪，
   把 `DRAW_JOG_TOOL_ENABLE` 改成 1（默认 0，因为夹爪里夹着笔）。
10. **示教点的有效范围**：`DRAW_POINT_TOL 0.8`（评分要求"进入有效范围即算过点"）
    要与卷面给的有效范围核对；评分还看线段直线度、连续性、平稳性与用时，
    所以上机试画时应记录 `drawLastRunMs()` 与 `drawLastPointsHit()`。
11. **绘图与取放/录制的互斥**：绘图期间摇杆整段让位（示教例外，由绘图模块自己读），
    所以若发现"示教时推杆没反应"，先确认按键/串口是不是处于录制或播放状态。
12. **裸 UART 后端（本轮新增，风险最高的一项）**：release 构建不再用
    Arduino `Serial`，直接操作 `UDR0`/`UCSR0A`/`UBRR0`，接收走 `USART_RX_vect`
    中断。上机第一步就要确认串口助手 115200-8N1 下能收发：发 `!` 应回
    `P=1 B=1 D=1`，发 `O`/`S` 应回 `OK`（v1.6.6 起删掉了带数值的 `OK #` 回复，
    与省 flash 的串口回复层收敛是同一轮）。若**完全没反应或全是乱码**，
    依次排查：(a) 串口助手波特率/换行符；(b) 烧录是否真的成功；
    (c) 用 `-DWEARM_SERIAL_ARDUINO=1` 重新编译烧录，退回官方串口库对照 ——
    如果退回后就正常，说明是这段裸寄存器代码的问题，把现象贴回来。
    另外长连发时环形缓冲只有 64 字节、行缓冲只有 40 字节，超了会丢字节。
13. ~~**地面坐标系的 `z` 与肩高**~~（**已作废**：串口 `x/y/z` 自 v1.6.4 起直接写
     三个舵机的角度，不再有地面坐标系与肩高常量，本节随
     `WEARM_SHOULDER_HEIGHT` 一起删除；坐标版备份见分支 `backup/xyz-cartesian`）。
14. **`R` / `P` 的新回复语义**：第一次 `R` 回 `OK` 表示开始录制（最长 38.4 s），
    第二次 `R` 若回 `DISCARD` 表示"没有位移/溢出，这段丢弃了"——不是故障。
    `P` 回 `EMPTY` 同理表示没有可回放的数据。真机上先录一段有位姿变化的动作
    （现在多短都行，只要末端走出 10 个坐标单位）再验证 `OK`。
15. **方向镜像对不对**（本轮新增）：基座与夹爪按"反向装配"处理了
    （`WEARM_MIRROR_BASE` / `WEARM_MIRROR_TOOL`，见上一节）。上机验证三件事：
    (a) 发 `O` 爪子**张开**、发 `S` **夹紧**（这一条错了就把 `WEARM_MIRROR_TOOL` 改 0）；
    (b) 左手柄左右推 / 串口给带 `x` 或 `y` 的坐标时，基座转的方向与机械现实一致
    （错了就把 `WEARM_MIRROR_BASE` 改 0）；
    (c) **A/B/C 取放是否去对了方向** —— 基座镜像会让 `PICK_SRC`/`PICK_DST` 里的 `±y`
    落到镜像侧，若发现取放跑反了，把 `pick_place.cpp` 顶部这些点的 `y` 取反
    （它们本就是"按现场摆放标定"的设计值）；
    (d) **上臂/下臂的上下方向**（默认 `WEARM_MIRROR_SHOULDER` / `WEARM_MIRROR_ELBOW`
    都是 0）：推左手柄前后（A1，上臂）与右手柄前后（A3，下臂），确认"逻辑角增大"
    对应的物理升降方向与直觉一致。**如果只有竖直方向反了、水平方向正常**，
    在串口发 `mS`（上臂）或 `mE`（下臂）就地翻转验证，确认后再把结果回写到
    `weArm_config.h` 的同名宏。
16. **摇杆中位自标定**：`joystickSetup()` 里取了 `JOY_CAL_SAMPLES`（v1.6.4 起 32）次平均，
    所以**上电/复位时不要碰摇杆**（碰了且偏差 > `JOY_CAL_MAX_OFF`（v1.6.4 起 80）会退回 512
    老行为，属于保守兜底，不是故障）。上机验证：手完全松开，观察 30 秒机械臂是否**完全不动**；
    再分别推四路轴确认方向与手感（v1.6.4 第二轮起应当是"**节奏恒定**：偏转只决定每格走多远，
    间隔固定 80/40/20 ms；静止要跨过 40+25=65 个计数才起控**"）。
    若某路仍然自己走，说明那路的静态偏差超过 `JOY_CAL_MAX_OFF`、或缓慢漂移速度超过了
    运行期跟踪（`JOY_TRACK_MS 20` 才挪一个计数），把 `joystick_control.cpp` 的 `JOY_CAL_MAX_OFF` /
    `JOY_DEADZONE` 调大后再试；想直接看 ADC，把同一文件的 `WEARM_JOY_DEBUG` 改 1
    （注意它要额外约 1.5~2KB flash，需同时关掉一个功能）。
17. **录制中直接按 `P` / 按键3**（本轮新增）：应当在**同一次**操作里"结束录制并开始
    播放"（回 `OK`）。若回 `DISCARD`，说明这段录制太短 / 没位移 / 超过 38.4 s
    溢出——按提示重录即可。
18. **录制深度改造后要上机确认的三件事**（本轮新增）：
    (a) **回放是否顺畅** —— 采样降到 200 ms 后靠 4 个 50 ms 子步插值展开，
    肉眼看应当与旧版（100 ms 采样）差不多；若明显一格格跳，把 `weArm_config.h`
    第 5 节的 `WEARM_REC_TICK_MS` 调回 100 或把 `BTN_PLAY_SUBSTEPS` 调大（改完
    复测容量；默认配置当前还剩 900 B flash（本轮工作区实测，v1.6.5 定版时是 1456 B），见
    `### 5) 实编容量` 一节的表）；
    (b) **长时间录制** —— 连续录 30 秒以上，看是否在 38.4 s 附近自动收尾并回
    `DISCARD`（写满判废，不留半段数据）；若需要更长就按第 5 节的账加条数
    （256 条 = 51.2 s，Data 81.5%，栈只剩约 378 B，风险自负）；
    (c) **SRAM 余量** —— Data 段已到 1443 B（70.5%），若出现莫名的随机复位/串口
    乱码（栈溢出典型症状），先把 `WEARM_REC_ENTRIES` 降回 96~128 再看是不是它。
19. **绘图轴向约定（本轮新增，最该先看的一条）**：5 张内置形状表已把 (u,v) 转置成
    (v,u)，约定 u→x = 纸面"上下"（+x 远离操作者）、v→y = 纸面"左右"（+y 向右）。
    上机画 `V`：应当是在**水平纸面上**、近端收口、两臂往远端张开的 V。
    若画出的是倒 V（开口朝远端），把 5 张表的 u 符号整体翻转；若是左右镜像，
    翻转 v 符号。**只能 5 张表一起翻**，只翻一两个会让字形之间自相矛盾。
    （这一条是因为用户上一轮反馈"画 V 字是在竖直平面上画"才改的，PC 探针只能证明
    "(u,v)→(x,y) 的映射一致"，证明不了纸面朝向，必须上纸看。）
20. **绘图与取放不在同一个固件里**（本轮新增）：`pick_place` 分支的绘图模块被编译掉，
    `F/D/G/E/Q/U/W` 与 `p/n/o` 没有绘图动作；`draw` 分支反之（没有 `A/B/C` 取放，
    发 `A` 不会有动作）。烧写前先确认自己在哪个分支，烧完发 `!` 看功能位。
    想一个固件里同时要两者：关掉按键模块（取放 + 绘图 + 按键关 = 31092 B，装得下）。
21. **上一轮的镜像/方向项仍然有效**：见第 15 条（基座/夹爪镜像、上臂/下臂方向可就地

### 附：小臂（`c`，摇杆 A3，舵机 D8）异常抖动 —— 可能原因与排查顺序

**本轮只做分析，未实装任何改动。** 先按"什么时候抖"分流，再往下查：

| 现象 | 更像哪一类 |
|---|---|
| 摇杆松手、无任务时自己一格格抽 | 摇杆 A3 静态偏差 / ADC 共地噪声 / 5V 纹波（软件侧已用死区 40 + 施密特 65 + 每 20ms 中位跟踪兜住） |
| 只在**承重**时抖（小臂伸出水平、笔压纸、末端挂物） | 舵机力矩不足 + 齿轮背隙（小臂 = 第二节臂，臂长 20，水平伸出时对 `c` 的重力力矩最大） |
| 只在**多个关节同时动**时抖 | 4 舵机共用一条 5V/地线，电压跌落 + GND 毛刺串进 ADC |
| 只在 c 接近 0°/180° 或 z 很低时"走一步停一步" | 是软限位整步拒绝的正常表现（`moveJointStep()` 返回 `MOVE_AT_LIMIT`），不是抖动；把 c 移回 90° 附近再看 |
| 高频小幅"嗡嗡" | 舵机内部电位器/齿轮磨损，或别的 ISR 长时间关中断（`servoDriveWrite()` 的 `cli()` 段） |

**按可能性排序的候选与验证动作**：

1. **力矩裕度最小**：`c` 的绝对角 = `r − c`（两节各 20 单位臂），小臂伸平时受力最大。
   验证：卸掉笔/负载，若抖动明显减轻 ⇒ 力矩/供电问题；换一颗同型号新舵机对比。
2. **四舵机共用 5V/地线**：Uno 板载 5V（USB 供电约 500 mA）带 4 个舵机同时起转会跌压。
   验证：舵机改独立 6V/≥2A 电源 + **共地**，并在舵机电源上并 1000 µF 电解电容。
3. **摇杆 A3 的静态偏差**：落在 41~64 计数时第二轮已用施密特 65 挡住；若某路偏差
   > `JOY_CAL_MAX_OFF 80`，`joystickSetup()` 会放弃该路标定并退回 512，残余偏差仍会被
   当成推杆。验证：`WEARM_JOY_DEBUG` 改 1，看 `raw A3=` 是否稳定落在 512±40；
   再把 A3 与 A1 插头对调 —— 抖动**跟着轴走**是摇杆/ADC，**跟着关节走**是机械/舵机。
4. **ADC 共地噪声**：ADC 与 4 路 PWM 同一块板，`c` 的电流在 GND 上产生毛刺会被采进 A3。
   验证：把 `JOY_DEADZONE` 临时调到 80，若抖动消失即印证；根治靠摇杆单独供电/加去耦。
5. **机械背隙/齿轮磨损**：断电后手推小臂，能感到明显空程就是它。
6. **软件侧基本可排除**：脉宽用绝对到期 tick（与 ISR 延迟无关）、帧长固定
   20000 tick = 20 ms、越界整步拒绝、中位跟踪每 20 ms 才挪 1 计数（≈25 计数/秒），
   都不足以产生肉眼可见的高频抖动。

**若将来要治（本轮不实装）**：硬件优先（独立舵机电源 + 电容、小臂换更高力矩舵机）；
固件可选——给 `moveJointStep()` 前的目标加一条 slew-rate 限幅、静止时不重复下发同一
脉宽（`servoDriveWrite()` 同值短路）、给 A3 单独做软件中值滤波。

## 单文件整合 —— `.selfcheck/make_single.ps1` 与 `single/meArm/meArm.ino`

需求是"把全部代码放进一个 .ino"。`.selfcheck/make_single.ps1` 把 11 个头文件
（先声明）、9 个实现文件（后定义）、最后根目录 `meArm.ino` 依次拼接，生成自包含的
`single/meArm/meArm.ino`（338092 B / 7344 行，带
`// Generated by .selfcheck/make_single.ps1. Do not edit this file directly.` 头）。

**模块化版本仍是唯一手写源，单文件是生成物，不要直接编辑**——改完源码重跑：

    powershell -NoProfile -ExecutionPolicy Bypass -File .selfcheck\make_single.ps1

拼接规则：

- 只在本文件内去掉 `#include "..."` 与 `#include <Arduino.h>`；每个系统头
  （`math.h`/`string.h`/`avr/io.h` …）只在**首次**出现处保留，文件开头统一补一次
  `#include <Arduino.h>`
- 每段前加 `// ===== <文件名> =====` 分隔注释，便于与模块化版逐段对照
- 顺序固定：头文件族 → 实现 → sketch。`avr_build.ps1` **不生成** Arduino 函数原型
  （ar2cpp 那一步的自动原型插入我们没有用），所以必须"先声明后使用"

**唯一的真冲突及处理**：`static double clampDouble(double,double,double)` 在
`constant_and_positions.cpp:192` 附近（带 `__attribute__((noinline))`）与
`draw_control.cpp:243` 附近各有一份。分 TU 编译合法，合进同一个 TU 就是 redefinition，
所以生成器把 `draw_control.cpp` 里的这份**逐行重命名为 `drawClampDouble`**
（脚本里的 `-replace '\bclampDouble\b'` 规则）。另一对同名函数 `beginMove`
（`pick_place.cpp` 与 `draw_control.cpp`）**不用改**：两边签名不同
（`(int,const double*,int)` 与 `(int,double,double,double)`），本身就是合法重载。
根目录 `*.cpp/*.h` 里 238 个 `static` 名字逐个查过，只有这两处重名。

**同一个 TU 里的宏重定义（独立复核发现，已修）**：`BTN_DEBOUNCE_MS` 原本在
`joystick_control.cpp:74`（30 ms）与 `button_control.cpp:84`（25UL）各定义一次。
分 TU 编译互不相干，合并成一个 TU 后严格编译会报
`warning: 'BTN_DEBOUNCE_MS' redefined`（`avr_build.ps1` 带 `-w` 不显示，
Arduino IDE 用户会看到）。两处的使用点都在各自定义之后，当前语义没受影响，
但这正是"合并才暴露出来的隐藏坑"，所以把摇杆模块那份改名为
`JOY_BTN_DEBOUNCE_MS`（定义 + 2 处注释 + `buttonDown()` 里的使用，共 4 处）。
现在单文件在 `-std=gnu++17 -Wall -Wextra -Wshadow -Wconversion` 下同样零警告。

**实测（16 MHz Uno / avr-gcc 7.3.0 + core 1.8.8）**：

| 构建 | Program | Data |
|---|---|---|
| 模块化（`-SketchDir D:\dsh1\meArm`） | 31356 B | 1443 B |
| 单文件（`-SketchDir D:\dsh1\meArm\single\meArm`） | 31356 B | 1443 B |

两者本轮完全相同（v1.6.4 时单文件还多 +12 B 的 LTO 内联顺序差）。**上表是本轮工作区实编值**
（v1.6.5 定版是两行都 30800 B / 1419 B）：相对 v1.6.5 各 **+556 B**、Data 各 **+24 B**
（恢复 `rangeLimit` 盒子那三条判据），相对 v1.6.4（模块化 32016 / 单文件 32028、Data 1475）
两行各 **−660 / −672 B**、Data 各 **−32 B**。
另外三档配置（按键关 / 绘图关 / 取放关）的对比见 `weArm_config.h` 顶部与
`### 5) 实编容量`。
生成器**幂等**：重跑到临时目录得到的文件与 `single/meArm/meArm.ino` 的 SHA256 相同
（当前 `8B034711…`，308362 B / 6825 行；v1.6.5 是 `BBE60B06…`，301756 B / 6713 行；
v1.6.4 是 `EE53561B…`，338092 B / 7344 行；v1.6.3 tag 里是 `EA1C32C1…`，332015 B / 7310 行）。
它逐字节复制源文件，所以**只看 HEAD 就能复现**——生成并提交产物前先确认
`git status` 干净：工作区里任何未提交改动都会被原样抄进单文件，产物就与 HEAD 对不上了。

换行符也是这条"可复现"的一部分：脚本**固定写 LF**（`[string]::Join("`n", …)` +
`WriteAllText`）。`.gitattributes` 已声明 `* text=auto eol=lf`，而 `WriteAllLines` 在
Windows 上写的是 CRLF，于是工作区文件（339304 B）与入库 blob（332015 B）字节不同、
每次 `git add` 都冒一条 CRLF→LF 警告。改成 LF 之后工作区文件 = 检出文件 = blob，
三者逐字节相同。
自包含性（只留 `meArm.ino` 也能编）、函数完整性、`#if WEARM_ENABLE_*` 门控一致性与
模块化回归由独立复核流程复跑确认，记录见 `.selfcheck/out/single_ino_verify.md`
（该目录不入库）。单文件版的上机确认项与模块化版完全相同，见上一节。

## 初始位姿改回 (40,0,0) —— 上电仍是 x90,y90,z90

用户要求（原话）：**"初始状态下控制位姿三舵机的角度：x90,y90,z90"**。

上一轮把 `POS_HOME` 改成 `{20,0,-10}` 之后，上电写进舵机的是 **90 / 60.55 / 7.42**（折叠
回缩姿态），与用户标定的上电初始状态不是同一个物理姿态。对照 v1.6.5（`main` = tag，提交
`edec161`）：那一版 FK 是错的（`alpha = r`、`beta = r − c`），但 `POS_HOME = {20,0,20}`
在它的映射下反解出来**正好**是 (90,90,90) —— 也就是说 v1.6.5 的上电物理姿态本来就是
90/90/90，只是被错误模型**显示**成 (20,0,20)。修正模型后，同一个物理姿态的坐标是
`(40,0,0)`（α=β=θ=0 ⇒ ρ=40、z=0），恰好落在可达外边界 ρ = L1+L2 = 40 上。

### 改了什么

1. **`constant_and_positions.cpp:30`**：`static const REC POS_HOME = { 40, 0, 0 };`；
   上方 `:19-29` 的注释写明用户要求、边界位置、副作用（无法再向外伸、就地垂直抬升
   无解）与历史（曾改 (20,0,-10)，已改回）；`:401-404` 与 `:444-446` 两处"工作空间
   内部"的说法改成"在可达外边界上、`limit` 是闭区间、能解出 90/90/90"。
2. **取放适配（`pick_place.cpp`）**：新初始位姿上"就地垂直抬升"除 z=0 外无解，于是
   新增 `static bool s_riseAtSrc`；`planTravelZ()` 里改成
   `const bool riseInPlace = pathCorePointOk(fromX, fromY, z, &b, &r, &c);`
   `if (!riseInPlace && !pathCorePointOk(src[0], src[1], z, &b, &r, &c)) continue;`
   并在返回前记录 `s_riseAtSrc = !riseInPlace;` —— 起点正上方不可达时，首段退化为
   "物体正上方(飞行高度)"。`pickPlaceStart()` 的 `path[1][0/1]` 与首段目标 `up[0/1]`
   都按 `s_riseAtSrc` 取，A/B/C 的飞行高度不变（**−7.50 / +12.50 / +29.50**）。
3. **探针**：`probe_move.cpp:66-73` 起点核对改 `(40,0,0)` 并**新增**一条断言
   "home 的三个位姿舵机角 = 90/90/90"；`:198-203` 盒子测试改成两条 —— "位于可达
   边界的 (40,0,0) 被点校验接受（±40 是闭区间）" + "盒内普通点 (20,0,-10) 通过"；
   `probe_draw.cpp:750-753` 抬笔起点期望改 `(40,0,0)`。其余探针（`probe_button`、
   `probe_pick_place`、`probe_pins_off`、`wearm_ino_test`）都用 `posGetHomeAngles()`
   自洽比较，无需改动。
4. **注释同步**：`meArm.ino:140-142`、`joystick_control.h:58-59`、`draw_control.cpp:67-70`。
